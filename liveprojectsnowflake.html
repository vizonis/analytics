Introduction

What is Snowflake?

A cloud-native data platform providing data warehousing, data lakes, data sharing, and data applications on one unified platform.

Fully Cloud-Native

No hardware to manage. Runs on AWS, Azure, or GCP — your choice.

Separation of Compute & Storage

Scale compute up/down instantly without touching storage costs.

Multi-Cluster Shared Data

Multiple compute clusters access the same data without performance loss.

Pay-Per-Second Pricing

Only pay for compute resources you actually use — per second, not per hour.

Enterprise Security

End-to-end encryption, row-level security, column masking, and RBAC built in.

Native Data Sharing

Share live data with external organizations instantly — no copies or ETL needed.

Debugging

Troubleshooting & Debugging in Snowflake

Common errors you'll encounter and proven strategies to resolve them fast.

1

Invalid Identifier / Object Not Found

Check schema with SELECT CURRENT_SCHEMA(). Ensure correct database and schema with USE statements.

2

CAST Conversion Failed (VARCHAR to INT)

Raw data has non-numeric characters. Use TRY_CAST() — returns NULL instead of failing.

3

Ambiguous Column in JOIN

Always prefix columns with table aliases: e.employee_id instead of employee_id.

4

Warehouse Suspended / Timeout

Check warehouse status. Run ALTER WAREHOUSE COMPUTE_WH RESUME; or ensure auto-resume is enabled.

5

Query Running Too Slow

Check Query Profile in Snowsight. Look for large data scans, spill to disk, or join explosions.

6

Time Travel for Accidental Deletes

Recover dropped tables: UNDROP TABLE table_name; Query past data: SELECT * FROM t AT(OFFSET => -3600);

Bronze Layer

Bronze Tables — Raw Data

Source data with intentional data quality issues — this is what real-world raw data looks like.

bronze.employees
CREATE TABLE bronze.employees ( employee_id INT, first_name VARCHAR(50), last_name VARCHAR(50), email VARCHAR(100), department_id INT, job_title VARCHAR(100), hire_date VARCHAR(20), -- wrong type! salary VARCHAR(20), -- messy data! city VARCHAR(50) );

Phase 1: Data Cleaning

Text Functions — Clean Names & Extract Data

Using CONCAT, UPPER, LOWER, LEFT, RIGHT, SUBSTRING to clean raw bronze data into silver.

Clean Names (CONCAT, UPPER, LOWER)
CREATE TABLE silver.employees_clean AS SELECT employee_id, UPPER(first_name) AS first_name, UPPER(last_name) AS last_name, CONCAT(first_name,' ',last_name) AS full_name, LOWER(email) AS email, department_id, job_title, city FROM bronze.employees;
Extract Email Domain (RIGHT)
SELECT email, RIGHT(email, CHARINDEX('@', REVERSE(email)) - 1 ) AS email_domain FROM bronze.employees;
Extract Year & Month (LEFT, SUBSTRING)
-- Extract year from hire_date SELECT hire_date, LEFT(hire_date, 4) AS hire_year FROM bronze.employees; -- Extract month (SUBSTRING) SELECT hire_date, SUBSTRING(hire_date, 6, 2) AS hire_month FROM bronze.employees;
Find & Replace + Standardize (REPLACE, CASE)
-- Standardize city names SELECT REPLACE(city,'BLR','Bangalore') AS city_clean FROM bronze.employees; -- Standardize attrition flag SELECT employee_id, CASE WHEN attrition_flag IN ('Y','Yes') THEN 'Yes' ELSE 'No' END AS attrition_flag FROM bronze.attrition;
Phase 1: Data Cleaning

Fix Dates & Salary — Complete Silver Table

Converting messy VARCHAR fields to proper types and building the final silver table.

Fix Date Format (CAST)
-- Convert VARCHAR date to DATE type SELECT CAST(hire_date AS DATE) AS hire_date FROM bronze.employees;
Fix Salary (Remove symbols, CAST to INT)
-- Remove '₹' and ',' then convert SELECT CAST( REPLACE( REPLACE(salary,'₹',''), ',','' ) AS INT ) AS salary FROM bronze.employees;
silver.employees_final (Complete)
CREATE TABLE silver.employees_final AS SELECT e.employee_id, CONCAT(UPPER(e.first_name),' ', UPPER(e.last_name)) AS full_name, LOWER(e.email) AS email, CAST(REPLACE(REPLACE( e.salary,'₹',''),',','') AS INT) AS salary, CAST(e.hire_date AS DATE) AS hire_date, e.department_id, REPLACE(e.city,'BLR','Bangalore') AS city FROM bronze.employees e;

Key Takeaway

We applied 6 different SQL functions in a single query: CONCAT, UPPER, LOWER, CAST, REPLACE (nested). This is the real power of SQL transformations.

Phase 2: Calculated Columns

Derived Fields — Salary Bands & Experience

Creating business-meaningful columns using CASE expressions and DATEDIFF on silver data.

Salary Band (CASE Expression)
SELECT employee_id, salary, CASE WHEN salary > 100000 THEN 'High' WHEN salary > 50000 THEN 'Medium' ELSE 'Low' END AS salary_band FROM silver.employees_final;
Experience in Years (DATEDIFF)
SELECT employee_id, DATEDIFF(YEAR, hire_date, CURRENT_DATE()) AS experience_years FROM silver.employees_final;
◆

High Band

Salary above 1,00,000 — typically senior roles, critical to retain.

◆

Medium Band

Salary between 50,000 and 1,00,000 — mid-level, growth potential.

◆

Low Band

Salary below 50,000 — high attrition risk if combined with low rating.

Phase 3: Joins

Building the Gold Master Table

Combining silver employees with bronze reference tables using INNER and LEFT joins.

gold.hr_master — The Single Source of Truth
CREATE TABLE gold.hr_master AS SELECT e.employee_id, e.full_name, d.department_name, e.salary, p.rating, a.attrition_flag FROM silver.employees_final e INNER JOIN bronze.departments d ON e.department_id = d.department_id LEFT JOIN bronze.performance p ON e.employee_id = p.employee_id LEFT JOIN bronze.attrition a ON e.employee_id = a.employee_id;

INNER JOIN

Departments — every employee must have a valid department. Orphan records excluded.

LEFT JOIN

Performance — not all employees have a review yet. We keep them with NULL rating.

LEFT JOIN

Attrition — only exited employees have records. Active employees show NULL.

Phase 4: Reports

Business Insights — Attrition & Salary

Aggregate functions and GROUP BY to generate actionable HR analytics from the gold layer.

Attrition Rate by Department
SELECT department_name, COUNT(CASE WHEN attrition_flag='Yes' THEN 1 END) * 100.0 / COUNT(*) AS attrition_rate FROM gold.hr_master GROUP BY department_name;

Why This Matters

Departments with >20% attrition need immediate HR intervention. This query pinpoints exactly where.

Average Salary by Department
SELECT department_name, AVG(salary) AS avg_salary FROM gold.hr_master GROUP BY department_name ORDER BY avg_salary DESC;

Pay Equity Check

Compare avg_salary across departments doing similar work. Large gaps indicate potential pay inequity.

Phase 4: Reports

Business Insights — Performers & Risk Detection

Identifying top talent and predicting which employees are most likely to leave.

Top Performers (Rating = 5)
SELECT * FROM gold.hr_master WHERE rating = 5 ORDER BY salary DESC;
Attendance Analysis
SELECT employee_id, COUNT(CASE WHEN status IN ('Absent','A') THEN 1 END) AS absent_days FROM bronze.attendance GROUP BY employee_id ORDER BY absent_days DESC;
High-Risk Employees (Hidden Insight)
-- Logic: Low rating + Low salary SELECT * FROM gold.hr_master WHERE rating <= 2 AND salary < 50000;

Why This Query is Powerful

This is a predictive insight — employees with low performance ratings AND low pay are statistically most likely to attrite. HR can proactively intervene before they leave.

Phase 5: UNION

UNION — Combining Attendance Statuses

Standardizing fragmented status values (P/Present, A/Absent) into unified categories using UNION.

Combine Present + WFH
SELECT employee_id, 'Present' AS status FROM bronze.attendance WHERE status IN ('P','Present') UNION SELECT employee_id, 'WFH' AS status FROM bronze.attendance WHERE status = 'WFH';

Why UNION Here?

Raw data has inconsistent status codes: "P", "Present", "A", "Absent", "WFH". UNION lets us standardize into clean categories for reporting.

UNION vs UNION ALL

UNION removes duplicates. UNION ALL keeps all rows (faster). Use UNION ALL when you know there are no duplicates or want to keep them.

Rules for UNION

Both queries must have the same number of columns. Corresponding columns must have compatible data types. Column names come from the first query.

Phase 6: Views

Creating Views for Reusable Insights

Views are saved queries — no data stored, always reflect the latest data when queried.

vw_high_risk_employees
CREATE VIEW vw_high_risk_employees AS SELECT * FROM gold.hr_master WHERE attrition_flag = 'Yes' OR rating <= 2;
Using the View
-- Query the view like a table SELECT full_name, department_name, salary, rating FROM vw_high_risk_employees ORDER BY salary ASC;

Always Live Data

Unlike a table that stores a snapshot, a view re-executes the underlying query every time — always showing the latest data.

Security & Abstraction

Hide complex joins from end users. Grant access to the view without exposing the underlying gold or silver tables.

DRY Principle

Write complex filter logic once. Reuse it everywhere — dashboards, reports, other queries — without duplicating code.
