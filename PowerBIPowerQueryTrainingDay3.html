CONNECT SQL DATABASE

The most common enterprise data source — connect Power BI directly to SQL Server

Step-by-Step: SQL Server Connection

Works for SQL Server, Azure SQL, Amazon RDS, MySQL, PostgreSQL

1
Get Data → Database → SQL Server

For MySQL: Get Data → Database → MySQL. For PostgreSQL: Get Data → Database → PostgreSQL.

2
Enter Server Name

Local: localhost or .\SQLEXPRESS. Remote: 10.0.0.5,1433 (IP,port). Azure: myserver.database.windows.net

3
Enter Database Name

The specific database: Production, HR_Analytics, Sales_DW. Leave blank to see all databases.

4
Credentials

Windows Authentication (uses your AD login — most common in companies) OR Database Authentication (username + password). For Azure: use "SQL Server Authentication" with AAD credentials.

5
Choose Mode

Critical decision: Import or DirectQuery — explained in next section.

6
Select Tables

Navigator shows all tables/views. Select dbo.Brands, dbo.Categories, dbo.Products, dbo.Customers. Check "Select related tables" for auto-selecting related tables.

7
Transform Data or Load

Click Transform Data to open Power Query (clean data first) OR Load to go directly to the model.

Connection String (Advanced)
Data Source=localhost;Initial Catalog=Production;Integrated Security=SSPI;

You can copy-paste this in "Advanced Options" instead of filling fields. Useful for sharing connections with team members.

Chapter 02

IMPORT vs DIRECTQUERY

The most important decision when connecting — get it wrong and your entire report suffers

Import Mode

Copy data into Power BI's engine

Power BI copies ALL data from SQL into its own VertiPaq engine (in-memory columnar database). After loading, the SQL connection is no longer needed for querying.

  • Lightning-fast queries (milliseconds)
  • Full DAX & Power Query capabilities
  • Works offline after loading
  • Can handle 10M+ rows (compressed ~10x)
  • Data is a snapshot — must refresh for updates
  • Large datasets = long initial load time

DirectQuery Mode

Query SQL Server in real-time

Power BI does NOT store data. Every time you click a visual, it sends a SQL query to the server. The server does the work and returns results.

  • Always shows live/latest data
  • No data size limit (1B+ rows fine)
  • No initial load wait
  • Slower visuals (each click = SQL round-trip)
  • Limited DAX functions (no time intelligence calc)
  • Requires constant network connection
  • Puts load on SQL Server

Live Use Case: 10 Million Records

Why Import Mode wins for this scenario

What Actually Happens

SQL Table Size: 10M rows × 15 columns ≈ 2.5 GB uncompressed on disk.

Import Mode: Power BI reads 2.5 GB → VertiPaq compresses to ~45 MB (55x compression!) → stored in RAM. Load time: ~3-4 minutes. After that, every visual click: 50-200ms. Blazing fast.

DirectQuery: Zero load time. But every click sends a SQL query. Simple bar chart = SQL with GROUP BY on 10M rows. Response: 3-15 seconds. Users see loading spinners. Multiple users clicking = SQL Server crashes under load.

Verdict: For 10M records, Import Mode is the clear winner. 3-minute one-time load vs permanent slowness.

Quick Decision Guide

Use Import When:
  • • Data is under 1-2 GB compressed
  • • Data doesn't change every minute
  • • You need complex DAX measures
  • • You need offline access
  • • Multiple users viewing same report
Use DirectQuery When:
  • • Data is 50GB+ (too big for memory)
  • • Real-time/near-real-time needed
  • • Regulatory requirement: no data copy
  • • Dashboard is simple (no complex DAX)
  • • Few concurrent users (1-5)

Chapter 05

RELATIONSHIPS

Model View connections — tables stay separate, linked by keys, queried dynamically

∞

One to Many (1:N)

The most common relationship. One row in the "One" table matches many rows in the "Many" table. The "1" side has the Primary Key. The "N" side has the Foreign Key.

Production Examples

1 brand → Many products (Atlas has 100+ products)

1 category → Many products (Mountain Bikes has 80+ products)

1 customer → Many orders

1 order → Many order_items

1

Many to One (N:1)

The exact same thing as One to Many — just viewed from the other direction. Power BI shows "1:N" regardless. Many products → 1 brand. Many orders → 1 customer.

It's the Same Relationship

brands 1——∞ products is identical to products ∞——1 brands. Power BI always displays "1:N" with the cardinality dot on the "1" side. The cross-filter direction is what matters (single vs both).

1

One to One (1:1)

One row in Table A matches exactly one row in Table B. Used for splitting wide tables — e.g., employee basic info in one table, employee compensation in another.

Example

Employees (emp_id, name, dept) 1:1 Employee_Salary (emp_id, basic, hra, da). Each employee has exactly one salary record. Join key = emp_id on both sides. Both sides have unique values.

∞

Many to Many (M:N)

⚠️ Avoid this! Multiple rows in A match multiple rows in B. Creates ambiguous results and can cause incorrect aggregations. Power BI warns you with a yellow indicator.

Problem Example

Students ↔ Classes (without an enrollment bridge table). Student "Rahul" is in Math AND Science. Class "Math" has Rahul AND Priya. The relationship is ambiguous — Power BI doesn't know which student-class combinations are valid.

Solution: Bridge Table

Students 1:N Enrollment N:1 Classes. Convert M:N into TWO 1:N relationships using a bridge/junction table. This is the standard pattern.

Automatic Relationships

When you load multiple tables, Power BI auto-detects relationships based on:

  • Matching column names (e.g., "brand_id" in both tables)
  • Matching data types
  • One column being a primary key (unique values)
Production Auto-Detection

Load Brands + Products → Power BI auto-creates: brands[brand_id] 1——∞ products[brand_id]. Same for categories↔products, customers↔orders. It figures out 5 relationships automatically!

Manual Relationships

When auto-detection fails (different column names, same name but wrong columns), you create relationships manually in Model View:

  • Go to Model View (icon on left sidebar)
  • Click the column in Table A → drag to column in Table B
  • A dialog opens — verify cardinality and cross-filter direction
  • Click OK
When Manual Is Needed

Products has "brand_id" but Brands has "id". Different names → no auto-detection. You manually drag products[brand_id] → brands[id]. Also needed when auto-detect creates wrong relationships.

Chapter 06

WHEN TO USE JOINS vs RELATIONSHIPS

The #1 confusion for Power BI beginners — they solve different problems

Use MERGE (Joins) When...

  • You want a single flat table as output
  • You need to clean/transform the joined data further
  • Joining from different data sources (SQL + Excel + API)
  • You need Left/Right/Full Outer joins (not just inner)
  • Creating a denormalized/star schema table for the model
  • One-time operation — merge once, load once

Use RELATIONSHIPS When...

  • You want tables to stay separate but connected
  • Same source database — SQL handles the join at query time
  • You need dynamic filtering (click a brand → products filter automatically)
  • Multiple report pages using the same model (no re-merging)
  • Better performance — VertiPaq optimizes relationships natively
  • 1:N only — all relationships should be one-to-many

Production Database — The Right Approach

Since all tables come from the same SQL database, use Relationships — NOT Merge:

✅ DO: Use Relationships
  • • Load all 4 tables separately to the model
  • • Let Power BI auto-detect 5 relationships
  • • Click a brand → products filter → order_items filter
  • • Build a report with brand slicer, category chart, product details
  • • All filtering happens automatically via relationships
❌ DON'T: Merge Everything
  • • Don't merge all tables into one mega-table
  • • You lose the ability to filter across dimensions
  • • Report becomes rigid — can't add new visuals easily
  • • Duplicate data (brand_name repeated per product)
  • • Slower model with denormalized data

Exception: If you need to create a specific flattened export (e.g., "give me one table with all order details including brand and category names for the accounting team"), THEN merge. For interactive dashboards, always use relationships.

Assignment

APACHE LOGS PARSING

Parse unstructured Apache server logs into a clean, analysis-ready dataset using Power Query

Raw Log Format (apache_logs table)

Each row is a single unstructured string like this:

83.149.9.216 - - [17/May/2015:10:05:03 +0000] "GET /presentations/logstash-monitorama-2013/images/kibana-search.png HTTP/1.1" 200 73221 "http://semicomplete.com/presentations/logstash-monitorama-2013/" "Mozilla/5.0 (Macintosh; Intel Mac OS X 10_9_1) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/32.0.1700.77 Safari/537.36"

This single string contains: IP, timestamp, HTTP method, resource path, protocol, response code, size, referrer, user agent — all crammed together with spaces and special characters as delimiters.

Step-by-Step Solution

1

Extract IP Address

The IP is everything before the first space. Use Text Before Delimiter.

Text.BeforeDelimiter([log_column], " ")
Result

83.149.9.216

2

Extract Timestamp

Timestamp is between [ and ]. Use Text Between Delimiters.

Text.BetweenDelimiters([log_column], "[", "]")
Result

17/May/2015:10:05:03 +0000

3

Extract HTTP Method & Resource

The request is inside the first pair of double quotes. Extract it, then split by space.

// Step 3a: Extract everything in first ""
let request = Text.BetweenDelimiters([log_column], '"', '"')
// Step 3b: Split by space → first part = method, rest = resource
let parts = Text.Split(request, " ")
// Step 3c: HTTP Method = parts{0}
// Step 3d: Resource = parts{1}
Result

Method: GET | Resource: /presentations/logstash-monitorama-2013/images/kibana-search.png

4

Extract Response Code & Size

After the closing quote of the request, there are two numbers: response code and size. Use Text After Delimiter on the last quote, then split.

// After extracting the request string from "", get what comes after:
let afterQuote = Text.AfterDelimiter([log_column], '" ', {occurrence: 1})
// Split by space → first number = response code, second = size
let nums = Text.Split(Text.BeforeDelimiter(afterQuote, " "), " ")
Result

Response Code: 200 | Size: 73221

5

Extract Referrer & User Agent

Referrer = text inside second pair of quotes. User Agent = text inside third/last pair of quotes. Use Text.BetweenDelimiters with occurrence parameter.

// Referrer (2nd occurrence of "")
Text.BetweenDelimiters([log_column], '"', '"', {occurrence: 2})

// User Agent (3rd/last occurrence of "")
Text.BetweenDelimiters([log_column], '"', '"', {occurrence: 3})
6

Custom Column: Response Description

Add Column → Custom Column → Name: "Response Description"

if [Response Code] = "200" then "OK - The request has succeeded."
else if [Response Code] = "404" then "Not Found - The server could not find the requested resource."
else if [Response Code] = "500" then "Internal Server Error - The server encountered an unexpected condition."
else "Unknown - Code not mapped."
7

Change Data Types

Response Code→Text(Keep as text to preserve leading zeros, enable IF ELSE matching)
Timestamp→Date/Time(Power Query auto-parses "17/May/2015:10:05:03 +0000")
Size→Whole Number(Bytes as integer)
8

Custom Column: Size in MB

// Add Column → Custom Column → Name: "Size_MB"
Number.Round([Size] / (1024 * 1024), 2)
Result

Size: 73221 → Size_MB: 0.07 | Size: 1048576 → Size_MB: 1.00

9

Extract Hour & Create Time Period

// Add Column → Custom Column → Name: "Hour"
Date.Hour([Timestamp])

// Add Column → Custom Column → Name: "Time Period"
if [Hour] < 12 then "Morning"
else if [Hour] <= 14 then "Afternoon"
else if [Hour] <= 17 then "Evening"
else "Night"
