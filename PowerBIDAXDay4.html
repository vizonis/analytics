Chapter 01

WHAT IS DAX?

The formula language that turns Power BI from a drag-and-drop tool into an analytical powerhouse

DAX = Data Analysis Expressions

Microsoft's formula language for Power BI & SSAS

DAX is a library of 250+ functions used to create custom calculations in Power BI. While Power Query cleans data before it loads, DAX calculates after it loads — at query time.

DAX is NOT SQL. SQL processes rows one at a time. DAX operates on entire columns at once using the VertiPaq in-memory engine — calculating millions of rows in milliseconds.

Your First DAX Measure
Total Salary = SUM( HR[Salary] )

This one line creates a measure that dynamically sums salary. In a card → total salary. In a bar chart by City → total by city. One formula, infinite flexibility.

DAX Does Two Things

1. Custom Calculations

YTD revenue, profit margins, running totals, rankings, moving averages — things you cannot do with drag-and-drop alone.

2. Advanced Filtering

Apply filters inside formulas: "Salary total for only Active employees in Bangalore" — impossible with visual-level filters alone.

Chapter 04

THE EASY WAY TO LEARN DAX

Forget memorizing 250 functions. Follow this proven 5-step path.

1

Learn 6 Aggregate Functions First

Start with SUM, COUNT, MIN, MAX, AVERAGE, DISTINCTCOUNT. These are direct column operations — no complexity. You already know them from Excel. Just learn the DAX syntax.

You already know this
// Excel: =SUM(E2:E100) // DAX: Total = SUM( HR[Salary] ) // Same concept, just reference the column, not the range
2

Understand CALCULATE (The King of DAX)

CALCULATE is the most important function in DAX. It modifies filter context. Once you understand CALCULATE, you understand 60% of DAX. Spend 1 full week on just this function.

CALCULATE Pattern
Result = CALCULATE( // What to calculate SUM( HR[Salary] ), // How to filter HR[Status] = "Active", HR[Department] = "IT" )
3

Learn FILTER Function

FILTER returns a table. It's used inside CALCULATE for complex conditions that simple filters can't handle — like >, <, or multi-column logic.

FILTER Pattern
High Earners = CALCULATE( COUNT( HR[EmpID] ), FILTER( HR, HR[Salary] > 80000 ) )
4

Learn the X Functions (Iterators)

SUMX, COUNTX, AVERAGEX, MINX, MAXX — the "X" means "eXplicit iteration." They go row-by-row, do math, then aggregate. This is where DAX gets powerful.

Iterator Pattern
// Calculate Annual Cost = Salary × 12 for each row, then sum Total Annual Cost = SUMX( HR, HR[Salary] * 12 )
5

Understand Context (Row vs Filter)

This is the final boss of DAX learning. Once you understand that DAX has two "modes" — Row Context and Filter Context — and how CALCULATE bridges them, you'll be in the top 10% of Power BI users.

If you know SUMIF, VLOOKUP, and Pivot Tables — you're 50% ready for DAX

The Excel → DAX Translation Map

Every Excel function has a DAX equivalent. The logic is the same — only the syntax changes.

Excel DAX Key Difference
=SUM(E2:E100)SUM(HR[Salary])Column reference, not range
=COUNTA(A2:A100)COUNT(HR[EmpID])COUNT in DAX = COUNTA in Excel
=SUMIF(D:D,"IT",E:E)CALCULATE(SUM(HR[Salary]), HR[Dept]="IT")CALCULATE replaces SUMIF/COUNTIF
=AVERAGEIFS(E:E,D:D,"IT",F:F,"Active")CALCULATE(AVERAGE(HR[Salary]), HR[Dept]="IT", HR[Status]="Active")Multiple conditions as separate arguments
=E2*12 (dragged down)SUMX(HR, HR[Salary]*12)X functions replace "drag down" logic
Pivot Table → ValuesMeasures (auto-adapt)DAX measures work in ANY visual

What Feels Familiar

Function names: SUM, COUNT, MIN, MAX, AVERAGE are identical

IF function: IF(HR[Age]>30, "Senior", "Junior") — same as Excel

Math operators: +, -, *, / work exactly the same

AND/OR logic: && replaces AND(), || replaces OR()

What Feels Different

No cell references: You type HR[Salary] not E2

No dragging: X functions (SUMX) handle row-by-row automatically

Filter Context: Excel Pivot filters are visible. DAX filters are invisible — you must learn to "see" them

CALCULATE: No Excel equivalent. This is the #1 thing to learn fresh.

Chapter 09

FILTER CONTEXT vs ROW CONTEXT

The two invisible "modes" that control how every DAX formula calculates

The Simplest Analogy

FILTER CONTEXT = "Which rows?"

Before any calculation happens, Power BI first decides which rows to include. This is determined by your slicers, visual filters, and cross-filters.

Bar chart by Department: When the "IT" bar is being drawn, the filter context is automatically set to Dept = "IT". Only IT rows are "visible" to the measure.

ROW CONTEXT = "Current row"

When DAX evaluates a calculated column or an X function, it goes row-by-row. Each row is the "current row" — that's the row context.

Calculated Column: When DAX calculates row 3 (Amit), it only "sees" Amit's data. HR[Salary] means Amit's salary (88000), not everyone's.

Filter Context — Deep Dive

Where it comes from:

Slicers on the report page

Filters pane (visual-level, page-level, report-level)

Cross-filter from other visuals on the page

CALCULATE function (explicit filter modification)

Visual Example

You have a bar chart showing Total Salary by Department. The measure is simply SUM(HR[Salary]).

When drawing the "HR" bar, Power BI automatically sets filter context to Department = "HR". The SUM only sees Rahul (75000), Sara (68000), Arjun (71000). Result: 214,000.

You didn't write any filter — the visual created the filter context.

Row Context — Deep Dive

Where it comes from:

Calculated Columns (always has row context)

X functions like SUMX, FILTER (create row context)

NOT from visuals, NOT from slicers

Calculated Column Example

You create a calculated column:

Annual Salary = HR[Salary] * 12

DAX goes row-by-row:
Row 1: Rahul → 75000 × 12 = 900,000
Row 2: Priya → 95000 × 12 = 1,140,000
...and so on for every row.

The row context makes HR[Salary] mean "this row's salary."

CALCULATE: The Bridge Between Contexts

This is the most important concept in all of DAX. When CALCULATE is used inside a row context (like a calculated column or an X function), it performs Context Transition — it converts the row context into a filter context.

Without Context Transition
// Calculated Column — WRONG Dept Total = SUM( HR[Salary] ) // Every row shows 691,000 // (total of ALL rows — ignores row context)
With Context Transition
// Calculated Column — CORRECT Dept Total = CALCULATE( SUM( HR[Salary] ) ) // Rahul's row: 214,000 (HR total) // Priya's row: 297,000 (IT total)

CALCULATE with no filter arguments still does something powerful — it transforms row context into filter context, so the SUM respects which department the current row belongs to.

Chapter 12

FILTER FUNCTION

The function that returns a filtered table — and the key to unlocking CALCULATE's full power

Understanding FILTER

FILTER is unique because it returns a table, not a value. You can't use FILTER alone as a measure — it needs to be wrapped inside another function like CALCULATE, SUMX, or AVERAGEX.

Syntax
FILTER( Table, // Which table to filter Condition // Which rows to keep (TRUE = keep) )

WRONG — FILTER alone

MyMeasure = FILTER( HR, HR[Salary] > 80000 ) // Error: Returns a TABLE, not a value!

CORRECT — FILTER inside CALCULATE

MyMeasure = CALCULATE( SUM( HR[Salary] ), FILTER( HR, HR[Salary] > 80000 ) )
Filter Context

FILTER Example 1 — Single Condition

// Total salary of Active employees only Active Salary Total = CALCULATE( SUM( HR[Salary] ), FILTER( HR, HR[Status] = "Active" ) )
How FILTER works here

1. FILTER scans the HR table row-by-row
2. For each row, checks: Is Status = "Active"?
3. Rahul → TRUE ✓ | Sara → FALSE ✗ | Priya → TRUE ✓
4. Returns a mini-table with only 7 Active rows
5. CALCULATE then runs SUM on those 7 rows

Result: 75K + 95K + 88K + 110K + 82K + 71K + 92K = 6,13,000

Note: For simple equality conditions, you don't actually need FILTER. CALCULATE(SUM(HR[Salary]), HR[Status]="Active") works the same. FILTER is needed for complex conditions (>, <, multi-column).

Filter Context

FILTER Example 2 — Greater Than (Needs FILTER)

// Total salary of employees earning more than 85,000 High Earner Salary = CALCULATE( SUM( HR[Salary] ), FILTER( HR, HR[Salary] > 85000 ) )
Breakdown

FILTER keeps rows where Salary > 85000: Priya(95K), Amit(88K), Vikram(110K), Kavitha(92K)

SUM of these = 95K + 88K + 110K + 92K = 3,85,000

You cannot write CALCULATE(SUM(HR[Salary]), HR[Salary] > 85000) — the > operator requires FILTER.

Filter Context

FILTER Example 3 — Multiple Conditions (AND)

// Active employees in IT department earning above 90,000 IT High Earners = CALCULATE( SUM( HR[Salary] ), FILTER( HR, HR[Status] = "Active" && HR[Department] = "IT" && HR[Salary] > 90000 ) )
Breakdown

FILTER checks ALL 3 conditions for each row:
Rahul: Active ✓ | IT ✗ → SKIP
Priya: Active ✓ | IT ✓ | 95K>90K ✓ → KEEP
Vikram: Active ✓ | IT ✓ | 110K>90K ✓ → KEEP
Kavitha: Active ✓ | IT ✓ | 92K>90K ✓ → KEEP

Result: 95K + 110K + 92K = 2,97,000

Filter Context

FILTER Example 4 — OR Condition

// Employees in IT OR Finance department IT or Finance Salary = CALCULATE( SUM( HR[Salary] ), FILTER( HR, HR[Department] = "IT" || HR[Department] = "Finance" ) )
Breakdown

Keeps rows where Dept is IT OR Finance: Priya(95K), Amit(88K), Vikram(110K), Neha(82K), Kavitha(92K)

Result: 95K + 88K + 110K + 82K + 92K = 4,67,000

Pro tip: For simple OR on same column, use IN operator: HR[Department] IN {"IT","Finance"}

Chapter 13

DAX OPERATORS

The symbols that connect conditions — used inside FILTER, IF, and CALCULATE

= Comparison Operators

Comparison

= (Equal To)

FILTER( HR, HR[Salary] = 95000 ) FILTER( HR, HR[Status] = "Active" )

Works with numbers and text. Text must be in double quotes. Returns: Priya (salary 95000), or all 7 Active employees.

Comparison

> (Greater Than)

FILTER( HR, HR[Salary] > 85000 ) FILTER( HR, HR[Age] > 30 )

Salary > 85K returns: Priya(95K), Amit(88K), Vikram(110K), Kavitha(92K). Age > 30 returns: Rahul(32), Amit(35), Vikram(40), Kavitha(33).

Comparison

< (Less Than)

FILTER( HR, HR[Salary] < 80000 ) FILTER( HR, HR[Age] < 30 )

Salary < 80K returns: Rahul(75K), Sara(68K), Arjun(71K). Age < 30 returns: Priya(28), Sara(26), Arjun(29).

Comparison

<= (Less Than or Equal)

FILTER( HR, HR[Salary] <= 82000 )

Returns: Rahul(75K), Sara(68K), Neha(82K), Arjun(71K). Neha at exactly 82,000 is INCLUDED.

Comparison

!= (Not Equal)

FILTER( HR, HR[City] != "Mumbai" ) FILTER( HR, HR[Status] != "Active" )

City != "Mumbai" returns 6 employees. Status != "Active" returns: Sara only.

Comparison

<> (Not Equal — SQL Style)

FILTER( HR, HR[Department] <> "HR" )

!= and <> are 100% identical in DAX. Dept <> "HR" returns 5 IT+Finance employees.

& Logical Operators

Logical

IN (Matches a List)

FILTER( HR, HR[Department] IN { "IT", "Finance" } ) FILTER( HR, HR[City] IN { "Mumbai", "Bangalore", "Chennai" } )

Uses curly braces { } for the list. Much cleaner than writing Dept="IT" || Dept="Finance".

Logical

NOT IN (Excludes a List)

FILTER( HR, NOT HR[Department] IN { "HR", "Finance" } ) FILTER( HR, NOT HR[City] IN { "Mumbai", "Delhi" } )

Place NOT before the column. NOT Dept IN {"HR","Finance"} returns only IT: Priya, Vikram, Kavitha.

Logical

&& (AND — Both Must Be True)

FILTER( HR, HR[Status] = "Active" && HR[Department] = "IT" ) FILTER( HR, HR[Salary] > 80000 && HR[Age] > 30 )

Replaces Excel's AND(). Active && IT returns: Priya, Vikram, Kavitha. Salary>80K && Age>30 returns: Amit, Vikram, Kavitha.

Logical

|| (OR — At Least One True)

FILTER( HR, HR[Salary] > 100000 || HR[Age] > 35 ) FILTER( HR, HR[City] = "Mumbai" || HR[City] = "Chennai" )

Replaces Excel's OR(). Salary>100K || Age>35 returns: Vikram(110K,40) only.

Putting It All Together — A Real HR Measure

Here is a real-world DAX measure that combines aggregates, FILTER, and multiple operators:

// "Total annual cost of Active IT employees // earning above 85K, plus 10% bonus, in Bangalore or Chennai" Premium IT Cost = SUMX( FILTER( HR, HR[Status] = "Active" && HR[Department] = "IT" && HR[Salary] > 85000 && HR[City] IN { "Bangalore", "Chennai" } ), HR[Salary] * 12 * 1.10 )
Step-by-step execution

1. FILTER checks each of 8 rows against ALL 4 conditions:
   Rahul: Active YES | IT NO = SKIP
   Priya: Active YES | IT YES | 95K>85K YES | Bangalore YES = KEEP
   Vikram: Active YES | IT YES | 110K>85K YES | Bangalore YES = KEEP
   Kavitha: Active YES | IT YES | 92K>85K YES | Chennai YES = KEEP
   Everyone else: SKIP

2. SUMX calculates for each kept row:
   Priya: 95000 x 12 x 1.10 = 12,54,000
   Vikram: 110000 x 12 x 1.10 = 14,52,000
   Kavitha: 92000 x 12 x 1.10 = 12,14,400

3. SUMX sums them up: 38,20,400

This single measure uses: SUMX (iterator), FILTER (filter context), = && > IN (4 operators). This is the level of DAX that gets you hired.
