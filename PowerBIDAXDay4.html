Chapter 01

WHAT IS DAX?

The formula language that makes Power BI infinitely powerful

DAX = Data Analysis Expressions

Microsoft's formula language for Power BI

DAX is a library of 250+ functions used to create custom calculations in Power BI. While Power Query transforms data before it loads, DAX calculates after it loads — at query time.

DAX is NOT SQL. SQL operates on tables row-by-row. DAX operates on entire columns at once using the VertiPaq engine. This is why DAX can calculate millions of rows in milliseconds — something that would take SQL minutes.

The Simplest DAX Measure
Total Salary = SUM( HR[Salary] )

This single line creates a measure that dynamically sums the Salary column. Put it in a card visual → it shows total salary. Put it in a bar chart by City → it shows total by city. One formula, infinite flexibility.

DAX = Two Things Combined

1. Calculations (Measures)

Revenue, profit margins, YTD, MTD, rankings, moving averages — things you CANNOT do with drag-and-drop alone.

2. Advanced Filtering (Filter Context)

Apply filters inside formulas — "Calculate revenue for only Active employees in Seattle" — something drag-and-drop can't do either.

Chapter 03

THE EASY WAY TO LEARN DAX

For Non-IT People

You don't need a CS degree. DAX is closer to Excel formulas than programming. If you've ever written =SUM(), =IF(), =VLOOKUP() — you already know 30% of DAX.

  • DAX uses the same concept as Excel formulas — column references, functions, operators
  • Start with Aggregate functions (SUM, COUNT, AVERAGE) — they're identical to Excel
  • Learn incrementally — don't jump to CALCULATE or FILTER on day 1
  • Power BI's autocomplete helps — start typing =SUM( and it suggests everything

For Excel Users

You have the biggest advantage. DAX literally evolved FROM Excel's formula engine. Your X vs DAX transition is the shortest.

  • =SUM(A1:A100) → SUM(Table[Column]) — same concept
  • =IF(A1>"Yes","No") → IF(condition, true, false) — same logic
  • =COUNTIF(A:A,">Active") → CALCULATE(COUNTROWS(FILTER(HR, HR[Status]="Active")))
  • =SUMIFS(B:B,A:A,"Active") → CALCULATE(SUM(HR[Salary]), FILTER(HR, HR[Status]="Active"))
  • The leap is: Learn CALCULATE and FILTER — then you're 80% there

The Easy Way

Don't try to memorize all 250+ functions. Learn by category.

Phase 1 — Aggregates (1 week):
SUM, COUNT, MIN, MAX, AVERAGE, DISTINCTCOUNT — these are your foundation. 6 functions. Master them before anything else.
Phase 2 — X Functions (1-2 weeks):
SUMX, COUNTX, MINX, MAXX, AVERAGEX — these add row-by-row iteration. Learn only AFTER Phase 1 is solid.
Phase 3 — FILTER (1-2 weeks):
The magic function that enables conditional calculations. Combined with X functions, it gives you 90% of real-world capabilities.
Phase 4 — Time Intelligence (2 weeks):
TIMEINTELLIGENCE functions (TOTALYTD, SAMEPERIODLASTYEAR, DATEADD, DATESINPERIOD) — learn last after Phases 1-3 are rock solid.
You DON'T need all 250 functions. 20 functions cover 90% of real-world scenarios. The rest are for edge cases.

Chapter 04

DAX GETTING STARTED

The two concepts that make DAX powerful — and the #1 concept that confuses everyone

How a Measure Works

The building block of every calculation

A measure is a formula that answers a business question. Unlike calculated columns (which add a value to every row), a measure is evaluated dynamically based on context — what the user has selected, filtered, or sliced.

// Create: Modeling tab → New Measure
Total Salary = SUM( HR[Salary] )
How It Responds

→ Put in a card visual: Total Salary = $26,098,354 (sum of ALL employees)

→ Add City slicer → Select "Seattle": Total Salary = $4,284,670 (sum of Seattle employees only)

→ Add Gender slicer → Select "Female": Total Salary = $11,585,890 (sum of Seattle + Female)

Same formula, three different answers. That's the power of DAX. The formula doesn't change — the context changes.

FC

Filter Context

The invisible environment created by the user's interactions. When you click a slicer, select a chart element, or apply a filter — Power BI creates a filter context behind the scenes. DAX measures automatically respond to it.

Real Example
// This measure automatically responds to any filter
Total Salary = SUM( HR[Salary] ) // User clicks "Seattle" in City slicer // Power BI internally wraps it in: // CALCULATE(SUM(HR[Salary]), FILTER(ALL(HR), HR[City]="Seattle")) // You NEVER write CALCULATE — Power BI adds it automatically!
RC

Row Context

Works row by row. Used inside X functions (SUMX, FILTER). Each row is evaluated in the current filter context.

How SUMX uses BOTH contexts
// SUMX = row context + filter context
Total Bonus = SUMX( FILTER( HR, HR[Status] = "Active" ), HR[Salary] * HR[Bonus %] / 100 ) // For each Active row → calculate Salary × Bonus% / 100 → then sum them all // FILTER works in filter context (only Active rows) // SUMX iterates in row context (row-by-row evaluation) // Together = "For each Active employee, calculate bonus, then sum"
Most Confusing Part

The trickiest DAX concept: SUMX evaluates the expression row-by-row (row context) WITHIN the current filter context (filter context). Both work together, but they're fundamentally different concepts.

Chapter 05

AGGREGATE FUNCTIONS

The foundation — every DAX journey starts here. HR data examples for every function.

Non-X (Simple)
X Functions (Iterative)
Aggregate

SUM

Adds up all values in a column. The most basic and most-used DAX function. Works exactly like Excel's =SUM().

Total Salary = SUM( HR[Salary] ) // Result: $26,098,354 (sum of all 315 employees)
When to Use

Total revenue, total quantity, total orders, total bonus — anytime you need a single total number.

Aggregate

COUNT

Counts the number of rows. COUNT counts non-blank values (opposite of COUNTBLANK).

Total Employees = COUNT( HR[EEID] ) // Result: 315
When to Use

How many employees? How many orders? How many active employees? How many products? Headcount reporting.

Aggregate

MIN

Finds the smallest value in a column. Exact same as Excel's =MIN().

Lowest Salary = MIN( HR[Salary] ) // Result: $41,673 (Anthony Rodriguez, Quality Engineer)
When to Use

Cheapest product, lowest score, earliest hire date, minimum response time — anytime you need the bottom value.

Aggregate

MAX

Finds the largest value. Same as Excel's =MAX().

Highest Salary = MAX( HR[Salary] ) // Result: $258,426 (James Bui, Sr. Analyst)
When to Use

Highest revenue month, top performer salary, max order value — anytime you need the top value.

Aggregate

AVERAGE

Mean of all values. Same as Excel's =AVERAGE().

Avg Salary = AVERAGE( HR[Salary] ) // Result: $82,851 per employee
When to Use

Average salary, average order value, average response time, average age — anytime you need the mean.

Aggregate

DISTINCTCOUNT

Counts unique values only (no duplicates). Unlike COUNT which counts ALL non-blank rows.

Unique Cities = DISTINCTCOUNT( HR[City] ) // Result: 13 (Seattle, Chicago, Miami, Phoenix, Austin, Columbus, Beijing, Shanghai, Chongqing, Manaus, Rio de Janerio, Chengdu, Beijing)
COUNT vs DISTINCTCOUNT
COUNT(EEID)
→ 315
DISTINCTCOUNT(City)
→ 13

COUNT says "how many rows" — DISTINCTCOUNT says "how many unique values". Use DISTINCTCOUNT for counting categories.

Iterative (X Functions)

SUMX

The game-changer. Iterates row-by-row, evaluating an expression for each row in the current filter context, then aggregates the results. This is where DAX becomes 10x more powerful than drag-and-drop.

// Calculate total bonus amount for Active employees
Total Bonus Amount = SUMX( FILTER( HR, HR[Employee Status] = "Active" ), HR[Salary] * Number.From(HR[Bonus %]) / 100 ) // Step 1: FILTER reduces 315 rows → ~220 Active employees // Step 2: For each Active employee, calculate: Salary × Bonus% / 100 // Step 3: SUM all calculated values together
Result

257 Active employees × their individual bonus percentages. You CANNOT do this with SUM alone — SUM gives you ONE total regardless of filters.

SUM vs SUMX
SUM(Salary)
→ One number, ignores filters
SUMX(Salary × Bonus%)
→ Dynamic, respects filters
Iterative (X Functions)

COUNTX

Counts rows that satisfy a condition. Like COUNT but with conditional logic.

// Count employees earning above $100,000
High Earners = COUNTX( HR, HR[Salary] > 100000 ) // Result: 153 employees earn above $100K
Why Not COUNT(FILTER(..., ...))?

COUNT(FILTER(HR, HR[Salary]>100000)) would also return 153, but FILTER loads all rows into memory. COUNTX is optimized — it stops at the first match.

Iterative (X Functions)

MINX

Finds the minimum value across evaluated rows.

// Lowest paid Active employee
Min Active Salary = MINX( FILTER( HR, HR[Employee Status] = "Active" ), HR[Salary] ) // Result: $41,673 (Anthony Rodriguez, Account Representative)
Why Not MIN(FILTER(...))?

MIN(FILTER(HR, HR[Status]="Active")[Salary]) would need to evaluate ALL active rows first, then find the minimum. MINX finds it as it goes — much faster with large datasets.

Iterative (X Functions)

MAXX

Finds the maximum value across evaluated rows.

// Highest paid Active employee by city
Max Salary by Seattle = MAXX( FILTER( HR, HR[City] = "Seattle" ), HR[Salary] ) // Result: $219,693 (Joseph Moore, Vice President)
Why Not MAX(FILTER(...))?

MAX(FILTER(HR, HR[City]="Seattle")[Salary]) evaluates all Seattle rows first. MAXX stops at the first match.

Iterative (X Functions)

AVERAGEX

Average of evaluated rows. Think of it as SUMX / COUNTX.

// Average salary of Old Employees by gender Avg Old Male Salary = AVERAGEX( FILTER( HR, AND HR[Employee Group] = "Old Employee", AND HR[Gender] = "Male" ), HR[Salary] ) // Only Old Male employees' average salary
SUMX/AVERAGEX rule of thumb

Whenever you're calculating something "for a subset of data" (by department, by gender, by city) — that's a SUMX/AVERAGEX scenario. Never use on the entire dataset — always pair with FILTER.

Chapter 06

FILTER FUNCTION

The most important DAX function — the key to conditional calculations

FILTER Function

The foundation of conditional DAX

FILTER takes a table and returns a subset of rows based on conditions. It's always paired with another function — SUMX, COUNTX, MINX, MAXX, AVERAGEX.

FILTER( Table, Condition1, [Condition2, ... )

HR Examples Using FILTER

// Only Active employees FILTER( HR, HR[Employee Status] = "Active" ) // Returns 220 rows of active employees
// Only Seattle Active employees FILTER( HR, AND HR[City] = "Seattle", AND HR[Employee Status] = "Active" ) // Returns ~45 rows
Only Senior Managers earning over $150K FILTER( HR, AND HR[Job Title] contains "Manager", AND HR[Salary] > 150000 ) // Returns ~12 rows
Active employees from China earning over $100K FILTER( HR, AND HR[Employee Status] = "Active", AND HR[Country] = "China", AND HR[Salary] > 100000 ) // Returns ~30 rows
Total bonus for Female Directors Total Dir Bonus = SUMX( FILTER( HR, AND HR[Job Title] contains "Director", AND HR[Gender] = "Female" ), HR[Salary] * Number.From(HR[Bonus %]) / 100 )
Why FILTER + SUMX = Power Combo

SUM(FILTER(...)) = wrong. That aggregates the filtered table but returns ONE number. SUMX(FILTER(...)) = dynamic. It recalculates for every filter change. This combo is used in 90% of real-world reports.

Chapter 07

DAX OPERATORS

The comparison and logical operators used inside FILTER and conditional expressions

=

Equal

Exact match comparison.

// Equals check FILTER( HR, HR[Employee Status] = "Active" ) // Only rows where Status is EXACTLY "Active" (case-sensitive!)
Most commonly used operator in DAX. Note: it IS case-sensitive — "active" ≠ "Active"
>

Greater Than

Strictly greater than a value.

FILTER( HR, HR[Salary] > 100000 ) // Only rows where Salary > $100,000 (does NOT include $100,000 itself)
Remember: ">" means strictly greater than. Use >= for "greater than or equal to".
<

Less Than

Strictly less than a value.

FILTER( HR, HR[Salary] < 50000 ) // Only employees earning less than $50,000 (does NOT include $50,000)
<=

Less Than or Equal To

Less than OR equal. The "or equal" part is crucial — without it, you'd miss the boundary value.

FILTER( HR, HR[Salary] <= 75000 ) // Includes employees earning exactly $75,000 (that's the "equal to" part)
!= <>

Not Equal (Two Types)

Both != and <><> mean "not equal". The difference is how they handle null values.

// != ignores nulls FILTER( HR, Exit Date != "*" ) // Returns rows where Exit Date is not null (still employed)
<> also ignores nulls FILTER( HR, Exit Date <> "*" ) // Same result! FILTER ignores nulls in !=
Most Common Use

FILTER(HR, HR[Exit Date] != "*") is the #1 most used FILTER pattern. It means "show me everyone who hasn't left".

IN

In (List)

Check if a value is IN a list. Replaces multiple OR conditions with one clean function.

// Employees from specific cities FILTER( HR, LIST("Seattle", "Chicago", "Miami") ) // Returns ~85 rows from those 3 cities
The Alternative (worse)
// WITHOUT IN — the painful way (3 OR conditions) FILTER( HR, OR HR[City]="Seattle", OR HR[City]="Chicago", OR HR[City]="Miami" ) // Same result, but longer, harder to read, harder to maintain
Why IN is better

Shorter, cleaner, and Power BI optimizes it using bitmap index internally. Use IN for ANY list-based filtering.

NOT IN

Not In (Exclusion List)

Opposite of IN. Remove rows that match any value in the list.

Everyone EXCEPT Seattle FILTER( HR, NOT( HR[City] IN {"Seattle"} ) ) // Returns ~290 rows (all except Seattle employees)
When to Use NOT IN

Remove outliers. Exclude specific products, exclude test regions, remove inactive records. NOT IN is "Remove all of these from the result."

&&

AND (Logical AND)

Combine multiple conditions with AND (both must be true for a row to be included).

Active Seattle employees earning > $80K FILTER( HR, AND HR[City] = "Seattle", AND HR[Salary] > 80000 ) // All conditions must be true for a row to be included
The "AND" Pattern

Every time you have multiple conditions that ALL must be true → use AND. It's the bread and butter of DAX filtering.

||

OR (Logical OR)

At least ONE condition must be true for a row to be included.

Any of these cities FILTER( HR, OR HR[City] = "Seattle", OR HR[City] = "Chicago", OR HR[City] = "Miami" ) // Returns 85 rows (union of those 3 cities)
The "OR" Pattern

Use OR when any ONE condition qualifies a row for inclusion. "Show me records from ANY of these cities" = OR pattern.
