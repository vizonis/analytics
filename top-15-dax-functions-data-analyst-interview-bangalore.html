MODIFY FILTER CONTEXT

01. CALCULATE 01

The most important DAX function. Period. If a recruiter only has time for one question, it will be about CALCULATE. It modifies the filter context of an expression — allowing you to compute a measure under different conditions without changing the visual.

Syntax
CALCULATE( <expression>, [<filter1>], [<filter2>], ... )

// expression: any measure or aggregate
// filter: table or boolean expression that modifies context
Example — Sales in Karnataka only
Sales Karnataka =
    CALCULATE(
        [Total Sales],
        Sales[State] = "Karnataka"
    )

// Even if the visual shows all India, this measure
// only shows Karnataka sales in every cell

"Write a DAX measure to calculate total sales for the previous year, regardless of what year is selected in the slicer."

Answer
Sales Previous Year =
    CALCULATE(
        [Total Sales],
        SAMEPERIODLASTYEAR( Date[Date] )
    )

// CALCULATE removes the existing year filter
// and replaces it with "same period last year"

Using CALCULATE inside a row context without understanding context transition. When you write a calculated column and use CALCULATE, it automatically performs context transition — turning row values into filters. This is the #1 reason candidates get unexpected results. If you write CALCULATE(SUM(Sales[Amount])) inside a calculated column, it doesn't sum ALL sales — it sums sales for the current row's context. ADVANCED FILTERING

02. FILTER 02

While CALCULATE with a simple condition handles equality checks, FILTER is needed for complex conditions — comparisons like >, <, between, OR logic across multiple columns, or filtering a different table than the one being aggregated.

Syntax
FILTER( <table>, <filter_condition> )

// Returns a table with only the rows that meet the condition
// Almost always used INSIDE CALCULATE as a filter argument

"Calculate total sales for products where the price is greater than ₹5,000 AND the category is 'Electronics'."

Answer
High-Value Electronics Sales =
    CALCULATE(
        [Total Sales],
        FILTER(
            Product,
            Product[Price] > 5000
                && Product[Category] = "Electronics"
        )
    )

Using FILTER when a simple boolean would work. If you write CALCULATE([Sales], FILTER(Sales, Sales[Year] = 2024)) — this is unnecessarily complex. Just write CALCULATE([Sales], Sales[Year] = 2024). Only use FILTER when you need complex conditions or filter a different table. Interviewers will mark you down for this.

REMOVE FILTERS

03. ALL / ALLEXCEPT 03

ALL removes filters from a table or column. It's the opposite of FILTER — instead of adding filters, it removes them. This is essential for calculating percentages of totals, grand totals across dimensions, and comparisons.

Syntax
ALL( <table_or_column> )          // Removes ALL filters from table/column
ALLEXCEPT( <table>, <column1>, ... ) // Removes all EXCEPT specified columns

"Write a DAX measure to calculate each category's contribution to total sales (percentage of grand total)."

Answer
% of Total Sales =
    DIVIDE(
        [Total Sales],                              // Current context (filtered)
        CALCULATE( [Total Sales], ALL(Sales) )  // Grand total (all filters removed)
    )

// In a table visual by Category:
// Electronics row: Electronics Sales / ALL Sales = 35%
// Clothing row:     Clothing Sales / ALL Sales     = 22%
ALL

Removes every filter on the table. Use for grand totals and overall percentages.

ALLEXCEPT

Removes all filters except specified columns. Use for subtotals across specific dimensions.

ITERATOR (X FUNCTIONS)

04. SUMX (and Iterator Functions) 04

The "X" functions are iterators — they go row by row, evaluate an expression for each row, and then aggregate. SUMX, AVERAGEX, MINX, MAXX, COUNTX, CONCATENATEX all follow the same pattern. SUMX is the most commonly tested.

SUM (Aggregator)
SUM( Sales[Amount] )

// Adds up the Amount column
// Can't do row-level math first
SUMX (Iterator)
SUMX( Sales,
  Sales[Qty] * Sales[Price] )

// Multiplies FIRST per row
// THEN sums the results

"Calculate total revenue where revenue = quantity × price, but only for orders where the discount is greater than 10%."

Answer
Discounted Order Revenue =
    SUMX(
        FILTER(
            Sales,
            Sales[DiscountPct] > 0.10
        ),
        Sales[Qty] * Sales[Price] * (1 - Sales[DiscountPct])
    )

// Step 1: FILTER returns only rows with >10% discount
// Step 2: SUMX iterates those rows, computes Qty×Price×(1-Discount)
// Step 3: Sums all the row-level results

Using SUMX on the wrong table. The table you pass to SUMX determines the granularity of iteration. If you pass the Sales table, it iterates per order line. If you pass the Product table, it iterates per product (and you'll get wrong results because the row context is at the wrong level). Always think: "What is one row of this table?" before choosing the table argument.

RELATIONSHIP NAVIGATION

05. RELATED / RELATEDTABLE 05

When your data model has multiple tables connected by relationships, RELATED fetches a value from a related table (many-to-one direction) and RELATEDTABLE returns all matching rows (one-to-many direction).

Syntax
RELATED( <column_in_related_table> )         // Returns a single value
RELATEDTABLE( <related_table> )              // Returns a table of rows

"In a calculated column on the Sales table, add the Category name from the Product table (which is related to Sales via ProductID)."

Answer
// In Sales table, calculated column:
Category Name =
    RELATED( Product[CategoryName] )

// Follows the relationship: Sales → Product → CategoryName
// Each Sales row gets the category name of its product

Using RELATED when no relationship exists, or in the wrong direction. RELATED only works in the many-to-one direction (from the "many" side). If you try RELATED(Sales[Amount]) from the Product table without a relationship, you get an error. In that case, use CALCULATE(SUM(Sales[Amount])) instead — the relationship handles the filtering automatically.

RANKING

06. RANKX 06

RANKX is an iterator that assigns a rank to each row based on a value. It's one of the most frequently tested functions because ranking (top N customers, top products, performance tiers) is a universal business requirement.

"Rank all customers by total sales in descending order."

Answer
Customer Rank =
    RANKX(
        ALL( Customer ),              // Table to rank over
        [Total Sales],                   // What to rank by
        [Total Sales],                   // Value if ties (optional)
        DESC                              // Highest sales = Rank 1
    )

// Customer A: ₹50L → Rank 1
// Customer B: ₹42L → Rank 2
// Customer C: ₹38L → Rank 3

"Create a measure that shows only the top 3 customers by sales, and 'Others' for the rest."

Answer — Top 3 + Others pattern
Top 3 Label =
    IF(
        [Customer Rank] <= 3,
        MAX( Customer[Name] ),
        "Others"
    )

// Use this in a visual — shows top 3 names + "Others" group
// Combine with a parallel measure that sums "Others" sales
TIME INTELLIGENCE

07. DATEADD 07

Time intelligence functions are the second most tested category after CALCULATE. DATEADD shifts a date column by a specified interval — previous month, next quarter, 3 months ago, etc.

Syntax
DATEADD( <dates_column>, <number_of_intervals>, <interval> )

// interval: DAY, MONTH, QUARTER, YEAR
// number_of_intervals: positive (future) or negative (past)

"Write measures for: sales last month, sales 3 months ago, and the month-over-month growth rate."

Answer
Sales Last Month =
    CALCULATE(
        [Total Sales],
        DATEADD( Date[Date], -1, MONTH )
    )

Sales 3 Months Ago =
    CALCULATE(
        [Total Sales],
        DATEADD( Date[Date], -3, MONTH )
    )

MoM Growth % =
    DIVIDE(
        [Total Sales] - [Sales Last Month],
        [Sales Last Month]
    )

Using DATEADD without a proper Date table. Time intelligence functions require a dedicated Date table marked as such in the model (with contiguous dates, no gaps). If you try DATEADD on Sales[OrderDate] directly, you'll get errors or wrong results. Always create a separate Date table with CALENDARAUTO() or CALENDAR() and mark it as the date table.

PERIOD-TO-DATE

08. TOTALYTD / TOTALQTD / TOTALMTD 08

Year-to-date, quarter-to-date, and month-to-date calculations are the most common time intelligence requirement. Every CFO dashboard has YTD. Every interview tests it.

Syntax + Examples
TOTALYTD( <expression>, <dates_column> [, <year_end_date>] )

Sales YTD =
    TOTALYTD( [Total Sales], Date[Date] )

Sales QTD =
    TOTALQTD( [Total Sales], Date[Date] )

Sales MTD =
    TOTALMTD( [Total Sales], Date[Date] )

// For Indian FY (Apr-Mar), add the year_end_date:
Sales FY YTD =
    TOTALYTD( [Total Sales], Date[Date], "31-03" )

"Calculate YTD sales AND same period last year YTD sales, then compute the YoY growth."

Answer
Sales YTD       = TOTALYTD( [Total Sales], Date[Date] )

Sales LY YTD   =
    CALCULATE(
        TOTALYTD( [Total Sales], Date[Date] ),
        SAMEPERIODLASTYEAR( Date[Date] )
    )

YoY Growth %   =
    DIVIDE(
        [Sales YTD] - [Sales LY YTD],
        [Sales LY YTD]
    )
SAFE DIVISION

09. DIVIDE 09

Seems simple — but DIVIDE is tested in every interview because it handles division-by-zero gracefully. Using A / B directly in DAX returns an error when B is blank or zero. DIVIDE returns an alternate result instead.

Syntax
DIVIDE( <numerator>, <denominator> [, <alternate_result>] )

// If denominator is 0 or BLANK, returns alternate_result
// Default alternate_result is BLANK()

"Calculate profit margin percentage. Handle the case where revenue is zero."

Answer
Profit Margin % =
    DIVIDE(
        [Total Profit],
        [Total Revenue],
        0                    // Return 0 instead of BLANK when revenue = 0
    )

// ❌ WRONG: [Total Profit] / [Total Revenue]
//    → Returns ERROR when Revenue = 0
// ✅ RIGHT: DIVIDE handles it gracefully
CONDITIONAL LOGIC

10. IF / SWITCH 10

Conditional logic is everywhere in business DAX — categorizing, flagging, tiering. Use IF for binary conditions and SWITCH for multiple conditions (cleaner than nested IFs).

"Create a measure that categorizes customers into 'High Value' (sales > 50L), 'Medium' (20L-50L), 'Low' (< 20L)."

Answer — SWITCH is cleaner than nested IF
Customer Tier =
    SWITCH(
        TRUE(),
        [Total Sales] >= 5000000, "High Value",
        [Total Sales] >= 2000000, "Medium",
        "Low"
    )

// SWITCH(TRUE(), ...) acts like a CASE statement in SQL
// Each condition is evaluated in order — first match wins
CONTEXT CHECK

11. HASONEVALUE / SELECTEDVALUE 11

These functions check whether exactly one value is selected in the current filter context. Essential for avoiding errors in visuals where multiple values might be active.

Syntax
HASONEVALUE( <column> )          // Returns TRUE if exactly 1 value is filtered
SELECTEDVALUE( <column> [, <alternate>] ) // Returns the value if 1, else alternate

"Write a card visual that shows the selected customer's name, but shows 'All Customers' when multiple are selected."

Answer
Selected Customer =
    SELECTEDVALUE(
        Customer[Name],
        "All Customers"
    )

// 1 customer selected → shows "Tata Steel"
// 2+ customers or none → shows "All Customers"
HIERARCHY HANDLING

12. ISINSCOPE 12

ISINSCOPE is the modern replacement for HASONEVALUE in matrix visuals. It checks whether a specific column is in the current hierarchy level — critical for calculations that change behavior at different hierarchy levels (year → quarter → month).

"In a matrix with Year → Quarter → Month hierarchy, show YTD at month level, QTD at quarter level, and annual total at year level — all in one measure."

Answer
Dynamic Period Sales =
    SWITCH(
        TRUE(),
        ISINSCOPE( Date[Month] ),    TOTALMTD( [Total Sales], Date[Date] ),
        ISINSCOPE( Date[Quarter] ),  TOTALQTD( [Total Sales], Date[Date] ),
        ISINSCOPE( Date[Year] ),     [Total Sales],
        [Total Sales]                            // Default fallback
    )

// Month row  → shows MTD (e.g., Jan 1-15 only)
// Quarter row → shows QTD (e.g., Q1 total so far)
// Year row    → shows full year total
NESTED ROW CONTEXT

13. EARLIER 13

EARLIER is the most confusing DAX function — and therefore the most impressive to nail in an interview. It accesses the row context of an outer calculation when you're inside a nested row context (like FILTER inside a calculated column).

"In a calculated column on the Sales table, show the rank of each sale amount within that customer's orders."

Answer
Sale Rank per Customer =
    RANKX(
        FILTER(
            Sales,
            Sales[CustomerID] = EARLIER( Sales[CustomerID] )
        ),
        Sales[Amount],
        ,
        DESC
    )

// EARLIER = "the CustomerID of the CURRENT row (outer context)"
// FILTER = "only compare against same customer's other rows"
// RANKX = "rank by Amount within that filtered set"

Interview Pro Tip: If you can explain EARLIER correctly — that it refers to the outer row context, not "previous row" (its name is misleading) — you'll stand out from 95% of candidates. Most people think EARLIER means "previous row" like Excel's OFFSET. It doesn't. ADVANCED FILTER MODIFICATION

14. TREATAS 14

TREATAS applies filters from one table's column to another table's column — even when there's no relationship between them. It's an advanced function that signals deep DAX understanding.

"The user selects regions in a slicer from the Region table. Apply that selection to filter the Territory table, which has different region codes but no direct relationship."

Answer
Sales by Mapped Territory =
    CALCULATE(
        [Total Sales],
        TREATAS(
            VALUES( Region[RegionCode] ),     // What user selected
            Territory[RegionCode]              // Where to apply it (no relationship)
        )
    )

// TREATAS maps the filter values from one column to another
// No physical relationship needed between Region and Territory
BLANK HANDLING

15. COALESCE 15

COALESCE returns the first non-blank value from a list of expressions. Think of it as a DAX version of SQL's COALESCE or Excel's IFERROR chaining. Extremely useful for data quality — when you have multiple source columns and want to pick the first available value.

"Customer phone number can come from 3 sources: CRM, Order table, or Delivery table. Return the first non-blank value."

Answer
Customer Phone =
    COALESCE(
        RELATED( CRM[Phone] ),
        RELATED( Orders[Phone] ),
        RELATED( Delivery[Phone] ),
        "N/A"                                  // Fallback if all blank
    )

// Checks CRM first → if blank, checks Orders → if blank,
// checks Delivery → if all blank, returns "N/A"

FAQ

DAX Interview FAQ

Most asked questions about DAX interviews in Bangalore.

What is the most important DAX function for interviews?

CALCULATE is universally considered the most important DAX function for interviews. Every Bangalore recruiter tests CALCULATE because it's the foundation of advanced DAX — it modifies filter context, which is the core concept in DAX. If you understand CALCULATE deeply (including its interactions with ALL, FILTER, and context transition), you can answer 40-50% of all DAX interview questions.

How many DAX functions should I know for a data analyst interview in Bangalore?

You should deeply understand 15-20 core DAX functions and be familiar with another 20-30. The 15 functions covered in this guide cover 90% of what's asked. Beyond these, know basic aggregation (SUM, AVERAGE, COUNT), string functions (CONCATENATE, LEFT, RIGHT, SEARCH), and a few niche functions like TREATAS and GENERATE for senior roles.

What is the difference between SUM and SUMX?

SUM is an aggregator that works on a single column — it adds up all values in that column respecting the current filter context. SUMX is an iterator — it takes a table and an expression, evaluates the expression row by row, and then sums the results. SUMX can do everything SUM can, plus more (like row-level calculations before aggregation). For example, SUMX(Sales, Sales[Qty] * Sales[Price]) multiplies first per row, then sums. SUM cannot do this.

Can I learn DAX without knowing Power BI?

Technically yes — you can write DAX in Excel Power Pivot or SSAS Tabular. But practically, 95% of DAX jobs require Power BI proficiency. At Vizonis Academy, we teach DAX within the Power BI context because that's how you'll use it on the job and how it's tested in interviews. The visual feedback of seeing your DAX measure work in a Power BI dashboard accelerates learning enormously.

What is the difference between row context and filter context?

This is the most fundamental DAX concept. Row context exists when DAX iterates over rows — in calculated columns and inside X functions (SUMX, FILTER). It means "for each row, what are the values of this row's columns?" Filter context is the set of filters applied by visuals, slicers, and CALCULATE. It determines which rows of which tables are visible. The tricky part: CALCULATE performs "context transition" — converting row context into filter context inside a calculated column or measure. Understanding this is the difference between passing and failing a DAX interview.
