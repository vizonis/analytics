Chapter 03

How GA4 Tracks Every Micro-Interaction on JLR's Digital Properties

Google Analytics 4 is the foundation layer of JLR's analytics stack. But JLR doesn't use GA4 the way most companies do (i.e., slapping the default tag and calling it a day). Their GA4 implementation is enterprise-grade. Here's exactly how it works:

GA4's Event-Based Model: Why It's Perfect for Journey Tracking

Unlike Universal Analytics (GA3) which was session-based, GA4 is event-based. Every interaction is an event. This is fundamentally important for premium car buying because:

  • A "session" doesn't capture what matters — a customer might open the configurator, close it, come back 3 days later, and that's 2 sessions but 1 logical action
  • Events can carry custom parameters — JLR tracks which color was selected, which engine, what the total price was, all as parameters on a single event
  • Events can be combined into a single user journey using GA4's User-ID feature, even across devices

JLR's Custom GA4 Event Architecture

JLR's analytics team defined a custom event taxonomy with over 80 events. Here's a simplified version showing how the configurator tracking works:

ga4-event-configurator.json 
{
  "event_name": "jlr_configure_vehicle",
  "parameters": {
    "model": "range_rover_sport",
    "trim_level": "HSE",
    "exterior_color": "santorini_black",
    "interior_color": "ivory_ebony",
    "engine": "3.0_l_diesel_mhev",
    "accessories_count": 4,
    "total_configured_price": 14250000,
    "configuration_step": 7,
    "time_spent_configuring": 847,
    "is_saved": true,
    "is_shared": false,
    "journey_stage": "configuration",
    "user_id": "JLR_U_8847291"
  }
}

See the detail level? That single event carries 13 parameters. Now imagine this firing 50,000+ times per month across India alone. That's the scale of data JLR works with.

GA4 → BigQuery: Where the Real Magic Happens

GA4's standard interface is limited. JLR exports every single event to Google BigQuery (GA4's free export feature). This gives them:

  • Raw event data — no sampling, no aggregation limits
  • SQL access — their analysts can write SQL queries directly on GA4 data
  • Historical data — GA4's standard UI keeps data for 14 months; BigQuery keeps it forever
  • Join capability — BigQuery data can be joined with CRM data in Microsoft Fabric

Chapter 04

Microsoft Fabric: The Unified Brain Behind JLR's Analytics

If GA4 is the data collector, Microsoft Fabric is the brain. Launched by Microsoft in 2023, Fabric is the most significant update to the Microsoft data platform in a decade. JLR adopted it early — and here's why it's the perfect tool for unifying a complex customer journey.

The Problem Fabric Solves: Data Silos

Before Fabric, JLR's data lived in 6+ separate systems:

GA4 / BigQuery
Web & App Data
Salesforce CRM
Lead & Customer Data
Dealer Mgmt System
Inventory & Sales
Finance System
Loans & Payments
Email Platform
Campaign Data
Service System
Post-Sale Data

Each system had its own database, its own format, its own definition of "customer." A customer who was "hot lead" in Salesforce might be "inactive" in the dealer system. Microsoft Fabric eliminates this.

How Microsoft Fabric Works: OneLake, One Copy

Fabric's core innovation is OneLake — a single storage layer that all Fabric workloads share. Think of it as "one copy of data, many ways to use it."

Power BI Dashboards
Real-time visualizations for executives, marketers, and dealer managers
Data Science / ML Models
Churn prediction, lead scoring, next-best-action recommendations
Real-Time Analytics (KQL)
Live streaming analytics for website activity and dealer interactions
Data Factory (ETL Pipelines)
Ingesting, cleaning, and transforming data from GA4, CRM, dealer systems
OneLake — Single Storage
One copy of unified data. All workloads read from here. No data duplication.

What JLR Built in Fabric: 4 Key Workloads

01 — Data Engineering

Automated pipelines pull GA4 data from BigQuery every 30 minutes, CRM data every hour, and dealer data daily. All data is cleaned, deduplicated, and unified using a customer master ID. Built using Fabric's Data Factory with Spark notebooks.

02 — Data Science

A lead scoring model (Python, trained on 3 years of historical data) predicts which configurator users are most likely to convert. A churn prediction model flags customers who go silent at the negotiation stage. Both run as automated ML experiments in Fabric.

03 — Real-Time Analytics

Using Fabric's Real-Time Analytics with KQL (Kusto Query Language), JLR monitors live website activity. If a high-intent user (someone who configured a car and saved it) returns to the site, the dealer gets a real-time notification within 60 seconds.

04 — Business Intelligence

Power BI dashboards (built on Fabric's DirectLake mode) give executives, marketing teams, and dealer managers self-service analytics. No waiting for reports. The data is always fresh, always unified, always accurate.

How does JLR use GA4 for customer journey tracking?

JLR uses GA4's event-based model to track every micro-interaction across their website — from model exploration to test drive booking, configurator usage, and lead submission. Each touchpoint is mapped to a specific GA4 event with custom parameters (like vehicle model, color choice, configured price). What is Microsoft Fabric and why does JLR use it?

Microsoft Fabric is a unified analytics platform that combines data engineering, data science, real-time analytics, and business intelligence into a single service with a shared storage layer called OneLake. JLR uses it because they had data silos — GA4 data in BigQuery, customer data in Salesforce, dealer data in a separate system, finance data elsewhere. Fabric unifies all of this into one place, enabling cross-system analysis like "which website behavior leads to the highest dealer conversion rate."
