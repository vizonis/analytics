Chapter 01

SEMANTIC MODEL & REFRESH

The dataset is now called a "Semantic Model" — and keeping it fresh is the backbone of every dashboard

Semantic Model — Scheduled Refresh Settings
What Is a Semantic Model?

Formerly called a "Dataset". It's the data model + relationships + DAX measures + M queries — everything that defines how data is structured and calculated. Visuals consume the semantic model, not raw tables.

Refresh Now

Manual, one-time refresh. Go to workspace → "⋯" on semantic model → "Refresh Now". Power BI reconnects to the data source, runs all M transformations, recalculates DAX, and updates the model. Takes seconds to minutes depending on data size.

Scheduled Refresh — Daily

Set one time per day (e.g., 8:00 AM). Pick timezone. The refresh runs after the dataset's last refresh completes. If data source is on-prem, the gateway must be online at that time.

Scheduled Refresh — Weekly

Pick specific days (Mon, Wed, Fri) + time + timezone. Maximum 48 scheduled refreshes per day for Pro. Premium allows up to 48/hour. Configure under Settings → Scheduled Refresh → Add another time.

Common Failures

Gateway offline = on-prem refresh fails. Credential expired = data source auth failed. Timeout = query took too long (>2hrs for Pro). Check Refresh History for error codes and timestamps.

Chapter 02

DIRECT QUERY & LIVE CONNECT

Skip the import — query the source in real-time, every time a user interacts

Import Mode (Baseline)

Data is copied into Power BI. Fast visuals. Stale until next refresh. Default mode.

Direct Query Mode

No data copied. Every click = SQL query to source. Always live. Slower if source is slow.

Live Connect (Analysis Services)

No import, no DAX editing. Connects to existing SSAS/Azure AS model. Model lives outside Power BI.

Direct Query — When to Use

Use when: data changes frequently (real-time needs), dataset is too large to import (50GB+), or compliance requires no data copies. Limitations: no M transformations in Service, limited DAX (no time-intel in some contexts), slower visuals if source DB is slow.

Live Connect — When to Use

Use when your org already has an SSAS Tabular or Azure Analysis Services model maintained by a separate team. Power BI becomes a viewer only — no model editing, no M, no DAX changes. All modeling happens in SSAS.

Real-Time vs Near-Real-Time

Direct Query = near-real-time (queries on each interaction, few seconds delay). Push datasets + Streaming = true real-time (milliseconds, via REST API or Event Hubs). For stock prices, IoT sensors → use Push datasets, not Direct Query.

Live Update of Records

With Direct Query, when a record is INSERTED/UPDATED/DELETED in the source DB, the next user interaction sends a fresh SQL query → they see the new data. No refresh needed. But there's no push notification — users must interact to trigger the query.

Chapter 03

LOCAL DATA & GATEWAY

Your Excel file is on your laptop, but your dashboard is in the cloud — the gateway bridges them

The Problem — Without Gateway
The Solution — With On-Premises Data Gateway
Gateway Installation

Download from: Power BI Service → "⋯" → Gateways → New gateway → Download installer. Run On-premises data gateway (standard). Install on a machine that: is always on, has network access to data sources, and has .NET 4.7.2+.

Gateway Setup — Sign In

After install, the Gateway Configuration window opens. Sign in with the same account that has Pro/Premium license. Choose "Register a new gateway" → Name it (e.g., "HR-Gateway") → Recovery key (SAVE THIS — you can't recover without it).

Gateway Setup — Add Data Source

In the gateway config: "Add data source" → Type: File / Folder (for Excel) or SQL Server → Enter path or server name → Authentication: Windows or Basic → Enter credentials → Test connection → Apply.

Configure in Power BI Service

In Service → Workspace → Semantic model → Settings → Scheduled Refresh → Expand "Data source credentials" → Select your gateway from dropdown → Map each data source to the gateway's data source → Apply. Scheduled refresh will now use the gateway.

Local Excel Refresh Automation

For local Excel files: the gateway reads the file at the exact path you configured. Keep the file in a shared network folder (not your personal Desktop). When someone updates the Excel file, the next scheduled refresh picks up the new data via the gateway.

Gateway Best Practices

Don't install on personal laptop — use a server. Keep gateway updated (check monthly). Use a service account for sign-in. Monitor via Gateway Health in Service. For clusters, use On-premises data gateway (personal mode) for Power Query Online.

Chapter 05

CAPACITIES & ADMIN ROLES

The infrastructure behind workspaces — and who controls it

Capacity Architecture
Capacity Definition

A capacity is a dedicated pool of compute resources (v-cores, memory, storage) that backs one or more workspaces. Pro workspaces use shared capacity (no guarantees). Premium workspaces use dedicated capacity (guaranteed resources, no throttling).

Capacity Admin

Manages the capacity itself: scale up/down, pause/resume, set auto-scale rules, view metrics (CPU, memory, queries/sec). Assigned via Admin Portal → Capacity Settings. Typically a platform/infra team role.

Workspace Admin

Manages content within a workspace: publish, share, set permissions, configure refresh. Can assign Viewer/Contributor/Member/Admin within their workspace. Does NOT manage capacity settings. This is a BI developer/lead role.

Tenant Admin

Organization-wide control: Admin Portal → Tenant settings (block sharing, enforce RLS, set default storage), audit logs, usage metrics, license management, create/delete capacities. Highest privilege — usually IT admin + BI lead.

Chapter 06

DEV / UAT / PROD ENVIRONMENTS

Never develop directly on production — use three workspaces with deployment pipelines

Three-Workspace Architecture
Parameters for Data Source

Instead of hardcoding "Server=Dev_SQL" in Power Query, create a parameter (e.g., ServerName) with values: Dev_SQL, UAT_SQL, Prod_SQL. Use ServerName in your M query. During pipeline deployment, swap the parameter value — same report, different data source.

How Parameters Work in Pipelines

Dev workspace: ServerName = "Dev_SQL". When deploying to UAT, the pipeline asks: "Replace Dev_SQL with?" → You enter "UAT_SQL". Pipeline swaps the parameter, updates dataset credentials, and rebinds the report — zero manual changes.

Workspace Permissions by Environment

DEV: Developers = Admin. UAT: Business users = Viewer, Dev lead = Admin. PROD: BI lead = Admin, End users = Viewer ONLY. Never give end users edit access to Prod.

Why Not Just One Workspace?

One workspace = broken dashboards during development. You change a column name in Dev → Prod report breaks. Three workspaces + pipelines = safe deployments, rollback capability, and audit trail of what changed between environments.

Chapter 07

DEPLOYMENT PIPELINES

The professional way to move content from Dev → UAT → Prod with zero errors

Deployment Pipeline — Interface
Configuration

Power BI Service → "Deploy pipelines" (left nav) → "New pipeline" → Name it → Assign workspaces to each stage (Dev, Test, Prod). All three workspaces must already exist. Premium required (Pro workspaces don't support pipelines).

Parameters Setup

In your Desktop .pbix: Home → Manage Parameters → New Parameter. Create parameters for server name, file path, database name. Reference them in Power Query: = Sql.Database(ServerName, DatabaseName). Publish to Dev workspace.

Deployment Step

In pipeline → click "Deploy" on the arrow → Select items → Set parameter rules (replace Dev values with UAT values) → Deploy. Pipeline: (1) copies report to target workspace, (2) updates dataset parameter values, (3) updates credentials, (4) rebinds report to new dataset.

Rollback

If something breaks in Prod, click "Swap" in the pipeline. Swap reverses the deployment — Prod gets the previous version. No need to re-deploy from UAT. This is why pipelines are non-negotiable in enterprise BI.

Chapter 08

APPS & END USER ACCESS

Workspaces are for builders — Apps are for consumers. This is how 500 people see your work.

Create App — Publish to End Users
How to Create an App

Workspace → "Create app" (top right) → Enter name, description, theme color → Choose navigation style (auto or custom) → Select content (dashboards + reports) → Set audience (Entire org, Specific people/groups, or security groups) → Publish app.

How End Users Access

Users receive an email notification. Or: Power BI Service → "Apps" in left nav → find the app → click to open. On mobile: install Power BI mobile app → app appears in the Apps tab. Users need Pro license (or workspace must be Premium) to view.

Update App

After updating the report in Prod workspace → go to the app → "Update app" → review changes → publish. End users see the updated version next time they open the app. You can set "Require approval" if governance demands it.

Workspace vs App

Workspace = the kitchen (messy, tools everywhere, builders only). App = the restaurant menu (curated, clean, consumers see only what you select). One workspace can have multiple apps (e.g., "HR Exec View" and "HR Analyst View" from the same workspace).

POWER BI INTERVIEW Q&A

The most asked questions — organized by topic with model answers

What is Power Query and why is it used in Power BI?

Power Query (M language) is the data extraction and transformation engine inside Power BI. It connects to 100+ data sources, applies transformations (filter, merge, append, pivot, split columns), and loads clean data into the semantic model. It's the ETL layer: Extract from source → Transform in PQ → Load into model. Without it, you'd load raw, dirty data directly into your visuals.

How do you connect different data sources in Power Query?

Get Data (Home ribbon) → Choose source type: SQL Server (enter server + database), Excel (browse file path), Web (URL), SharePoint, Azure Data Lake, OData, REST API, etc. Each source has its own connector with specific authentication (Windows, Basic, OAuth, Organizational account). You can connect multiple sources in one .pbix file.

What is the difference between Merge and Append in Power Query?

Merge = JOIN (SQL). Combines columns from two tables based on a common key. Types: Left Outer, Right Outer, Full Outer, Inner, Left Anti, Right Anti. Example: Employee table + Department table → merge on DeptID to get Dept Name column.

Append = UNION (SQL). Stacks rows from two tables with the same schema. Example: 2023 Sales table + 2024 Sales table → append to get one combined Sales table with all rows.

Name 5 common Power Query transformations.

1. Filter Rows: Remove nulls, top N, or by condition.
2. Remove Columns: Drop columns you don't need (reduces model size).
3. Split Column: Split "John Doe" into First Name + Last Name by delimiter.
4. Pivot Column: Convert row values to columns (e.g., month rows → month columns).
5. Replace Values: Fix data quality — replace "N/A" with null, "USA" with "United States".
Bonus: Group By (aggregate), Custom Column (M formula), Duplicate/Reference query.

What is DAX and how is it different from Power Query (M)?

DAX (Data Analysis Expressions) operates on the loaded data model — after Power Query has loaded it. DAX creates measures (aggregations like SUM, AVERAGE, CALCULATE with filters) and calculated columns (row-level). M (Power Query) operates during data load — connecting, cleaning, shaping. Rule of thumb: M for shaping data, DAX for calculating results.

Explain CALCULATE — why is it the most important DAX function?

CALCULATE modifies the filter context of a measure. Syntax: CALCULATE(expression, filter1, filter2, ...). Example: CALCULATE(SUM(Sales[Amount]), Sales[Year]=2024) = total sales only for 2024, regardless of what the user has filtered. It's the foundation for: YoY comparisons, ranking, dynamic grouping, and virtually every complex calculation. If you only learn one DAX function, make it CALCULATE.

What is the difference between calculated column and measure?

Calculated Column: Evaluated row-by-row during data load. Stored in the model (increases file size). Uses ROW CONTEXT. Example: Full Name = [FirstName] & " " & [LastName].

Measure: Evaluated at query time (when visual renders). Not stored (no size increase). Uses FILTER CONTEXT. Example: Total Sales = SUM(Sales[Amount]).

Best practice: Use measures whenever possible. Only use calculated columns when you need to use the result as a filter/slicer/relationship key.

How do Drill-through and Bookmarks differ?

Drill-through: Right-click a data point → navigate to a detail page filtered to that context. Example: Click "Engineering" in a donut chart → drill through to Employee Detail page showing only Engineering employees. Always one-way (detail → back to summary).

Bookmarks: Capture the entire visual state (filters, selections, visibility, page) as a named snapshot. Replay on button click. Example: "Profit View" bookmark hides cost column and filters to Profit > 0. Bidirectional — can bookmark any page state.

What are Parameters in Power BI and how are they used?

Parameters are user-controllable variables. Types: (1) Numeric — slider for threshold values (e.g., "Show top N customers"). (2) Text — dropdown for switching measures or dimensions. (3) Field Parameter — lets users dynamically swap fields in a visual (e.g., switch X-axis from Month to Region). Created via Modeling → New Parameter. Used in measures with SWITCH or SELECTEDVALUE.

What is Row-Level Security (RLS) and how do you implement it?

RLS restricts which rows a user can see based on their identity. Implementation: (1) Create a security table (UserEmail, Region). (2) Modeling → Manage Roles → New Role "Regional Manager" → DAX filter: [Region] IN VALUES('Security'[Region]). (3) In Service → dataset → Security → add users to roles. Users in "Regional Manager" role only see rows matching their region. Test in Desktop via "View as Role".

What are the best practices for designing a Power BI dashboard?

1. Fit on one screen (no scroll). 2. 5-8 visuals max — each answers a unique question. 3. Top-left hierarchy (KPIs top, detail bottom-right). 4. Consistent color language (green = good, always). 5. Remove chart junk (no 3D, no redundant legends). 6. Use slicers instead of duplicate filtered charts. 7. Dark theme for data density. 8. Mobile layout for phone users. 9. Performance: avoid too many visuals on one page. 10. Document with tooltips and bookmarks for navigation.

What is the difference between Publish and Deploy in Power BI?

Publish = one-way push from Desktop to a single workspace. Home → Publish → select workspace. Overwrites the existing report. Simple, no parameter swapping.

Deploy = via Deployment Pipeline, moves content across stages (Dev → UAT → Prod) with parameter value swapping. Supports selective item deployment, rollback (Swap), and rule-based parameter replacement. Professional-grade workflow.

Why do we need an On-Premises Data Gateway?

Power BI Service lives in Microsoft's cloud. If your data source is on-premises (local SQL Server, shared Excel file, local ERP), the Service cannot reach it directly. The gateway is a bridge software installed on your network that receives encrypted requests from the Service, forwards them to your local data source, and sends results back. Without it, scheduled refresh fails for on-prem data.

Explain the difference between Import, Direct Query, and Live Connect.

Import: Data is copied into Power BI at refresh time. Fast visuals. Data can be stale. Default mode. 1GB limit (Pro).
Direct Query: No data copied. Every user interaction generates a SQL query to the source. Always live but slower if source is slow. Limited M/DAX.
Live Connect: Connects to an existing SSAS/Azure AS model. No import, no model editing in Power BI. The SSAS model handles all queries. Used when a separate team manages the model.

What is the difference between a Workspace and an App?

Workspace = the development container. Has datasets, reports, dashboards, dataflows. Builders (Admins, Members) work here. Can be messy with test reports.
App = the curated, published interface for end users. You select specific dashboards/reports from a workspace, arrange navigation, and publish as an app. End users see a clean, focused experience. One workspace → multiple apps possible (e.g., "Exec View" vs "Analyst View").

POWER BI RESUME GUIDE

How to write a resume that gets you interviews — with a proven template

Lead With Impact

Don't write "Created dashboards in Power BI." Write: "Built 12 interactive dashboards serving 200+ users, reducing ad-hoc reporting time by 60%." Numbers + impact = interview magnet.

List Specific Tools

Don't just say "Power BI." Break it down: Power BI Desktop, Power Query (M), DAX, Power BI Service, Gateway, Deployment Pipelines, RLS, Incremental Refresh. Recruiters search by keyword.

Showcase Projects

Have a dedicated "Projects" section with 2-3 Power BI projects. For each: business problem → data sources → techniques used → business impact. Include links to published dashboards or screenshots.

Quantify Everything

Replace "Improved performance" with "Optimized DAX measures reducing refresh time from 45 min to 8 min." Replace "Cleaned data" with "Transformed 2M+ rows across 15 tables using Power Query."

Mention Data Sources

List the actual sources you've connected: SQL Server, Azure Data Lake, SharePoint, Salesforce API, SAP BW, Excel, CSV, Web scraping. This shows versatility recruiters look for.

Avoid Common Mistakes

Don't: list "MS Office" as a skill (assumed). Don't put a photo (in most markets). Don't use paragraphs — use bullets. Don't exceed 2 pages. Don't use generic objectives. Do: use a clean layout, consistent fonts, ATS-friendly format (no tables/columns).
