Top 10 Advanced Excel Formulas Every Data Analyst Must Know

Advanced Excel remains the #1 required skill in 94% of data analytics job postings in Bangalore. Not basic Excel — advanced formulas that handle real business data: messy datasets, dynamic lookups, conditional aggregations, and multi-criteria filtering. Here are the top 10 formulas we teach in depth at Vizonis Academy, each with 3 real-world examples you'll encounter in actual Bangalore companies.

01

XLOOKUP — The Modern Lookup That Replaced VLOOKUP

Why learn it: XLOOKUP is Microsoft's replacement for VLOOKUP and INDEX-MATCH combined. It can search in any direction (left, right, up, down), handle missing values gracefully, return entire arrays, and nest multiple lookups. In 2026, if you're still writing VLOOKUP in your interviews, you look outdated. XLOOKUP is 2x faster to write and 10x more flexible. Every Bangalore company that uses Microsoft 365 (which is virtually all of them) has XLOOKUP available.

Example 1: Employee Salary Lookup with Fallback
/* Find employee salary by ID, show "Not Found" if missing */ =XLOOKUP(E2, A:A, C:C, "Not Found") /* E2 = Employee ID to search | A:A = ID column | C:C = Salary column */
Example 2: Horizontal Lookup for Monthly Sales
/* Search across columns for a specific month's sales */ =XLOOKUP("Mar", B1:M1, B2:M2) /* B1:M1 = Month headers | B2:M2 = Sales values for that row */
Example 3: Nested XLOOKUP for Two-Way Lookup
/* Find revenue for a specific product in a specific region */ =XLOOKUP(F1, A2:A20, XLOOKUP(F2, B1:E1, B2:E20)) /* F1=Product | F2=Region | First XLOOKUP finds the row, second finds the column */
02

INDEX-MATCH — The Bulletproof Lookup Combination

Why learn it: Even though XLOOKUP exists, INDEX-MATCH is still asked in 60% of Bangalore data analyst interviews. Why? Because legacy Excel files (pre-2021) don't support XLOOKUP. Many companies in Bangalore — especially banking, manufacturing, and consulting — still run Excel 2016/2019. INDEX-MATCH also teaches you how range references work, which transfers to DAX, SQL, and Python. Understanding this formula makes you a stronger analyst overall.

Example 1: Basic Employee Name Lookup from ID
=INDEX(B:B, MATCH(E2, A:A, 0)) /* MATCH finds the row number of E2 in column A, INDEX returns column B at that row */
Example 2: Two-Way Lookup with Double INDEX-MATCH
=INDEX(B2:E20, MATCH(G1, A2:A20, 0), MATCH(G2, B1:E1, 0)) /* G1=Product name, G2=Month → returns intersection value */
Example 3: Left Lookup (VLOOKUP Can't Do This)
/* Get Employee ID when you only have the Employee Name (Name is to the right of ID) */ =INDEX(A:A, MATCH(E2, B:B, 0)) /* This is the #1 reason INDEX-MATCH beats VLOOKUP — it searches left */
03

SUMIFS — Multi-Conditional Summation

Why learn it: SUMIFS is the most frequently used advanced formula in corporate analytics. Every business report requires conditional aggregation — "sum sales for Bangalore region in Q1 for product category Electronics." SUMIFS handles this elegantly. It's also the conceptual foundation for DAX's CALCULATE function and SQL's GROUP BY with WHERE. Learn SUMIFS deeply and the other tools become 50% easier.

Example 1: Total Sales for Specific Region and Month
=SUMIFS(F:F, B:B, "Bangalore", D:D, "Jan") /* F=Sales, B=Region, D=Month → Sum sales where Region=Bangalore AND Month=Jan */
Example 2: Dynamic SUMIFS with Cell References
=SUMIFS(F:F, B:B, H1, D:D, ">="&I1, D:D, "<="&J1) /* H1=Region (from dropdown), I1=Start Date, J1=End Date → Dynamic date range sum */
Example 3: SUMIFS with Wildcard for Partial Match
=SUMIFS(F:F, C:C, "*Electronics*", B:B, "<>Mumbai") /* Sum sales where Category contains "Electronics" AND Region is NOT Mumbai */
04

FILTER — Dynamic Array Extraction

Why learn it: FILTER is a dynamic array formula (Excel 365/2021) that returns an entire filtered dataset, not just a single value. This is revolutionary for building interactive reports without Power BI. You can create drop-down driven dashboards entirely in Excel using FILTER. It's the Excel equivalent of SQL's WHERE clause and Power BI's filter context. Bangalore startups love this formula because it eliminates the need for pivot tables in many scenarios.

Example 1: Extract All Records for Bangalore Region
=FILTER(A2:F100, B2:B100="Bangalore", "No records found") /* Returns entire rows where Region column = Bangalore */
Example 2: Multi-Condition Filter with AND Logic
=FILTER(A2:F100, (B2:B100="Bangalore")*(F2:F100>50000), "") /* Filter rows where Region=Bangalore AND Sales > 50,000. * acts as AND */
Example 3: FILTER + SORT for Top N Analysis
=SORT(FILTER(A2:F100, F2:F100>100000), 6, -1) /* Filter sales > 1L, then sort descending by column 6 (Sales). Returns top performers. */
05

LET — Variable Assignment Inside Formulas

Why learn it: LET allows you to define variables inside a formula, making complex formulas readable, debuggable, and faster (Excel calculates named expressions once and reuses them). This is a game-changer for long nested IFs, multi-step calculations, and formulas that repeat the same sub-expression multiple times. It's the closest Excel gets to programming — and it directly maps to Python's variable assignment concept.

Example 1: Simplify Repeated Calculations
=LET( avgSales, AVERAGE(F:F), threshold, avgSales * 1.5, SUMIFS(F:F, F:F, ">"&threshold) ) /* Calculate average sales, define threshold as 1.5x average, sum all above threshold */
Example 2: Complex Conditional with Named Steps
=LET( emp, XLOOKUP(E2, A:A, B:B), dept, XLOOKUP(E2, A:A, D:D), bonus, IF(dept="Sales", 0.15, 0.10), emp & " - " & dept & " - Bonus: " & TEXT(bonus, "0%") ) /* Named variables make this 4-step calculation readable */
Example 3: LET with FILTER for Dynamic Reporting
=LET( data, A2:F500, region, H1, filtered, FILTER(data, INDEX(data,,2)=region, ""), ROWS(filtered) ) /* Count records for selected region — clean, modular, fast */
06

TEXTJOIN — Concatenate with Delimiters and Conditions

Why learn it: TEXTJOIN concatenates values from a range with a custom delimiter, optionally ignoring blanks. Combined with FILTER or IF, it becomes incredibly powerful for creating comma-separated lists, building SQL IN clauses from Excel data, generating email lists, and creating summary text from multiple rows. This is heavily used in Bangalore's consulting and e-commerce companies for creating tag lists, category strings, and stakeholder summary lines.

Example 1: Comma-Separated Product List for an Order
=TEXTJOIN(", ", TRUE, FILTER(C:C, A:A="ORD-1234")) /* Returns: "Laptop, Mouse, Keyboard" — all products for order ORD-1234 */
Example 2: Generate SQL IN Clause from Excel Data
"WHERE employee_id IN (" & TEXTJOIN(",", TRUE, "'"&A2:A50&"'") & ")" /* Generates: WHERE employee_id IN ('E001','E002','E003',...) — copy-paste into SQL */
Example 3: Create Summary Tags per Category
=TEXTJOIN(" | ", TRUE, UNIQUE(FILTER(D:D, B:B=F1))) /* For category in F1, returns unique sub-categories pipe-separated */
07

IFS — Clean Multi-Condition Logic Without Nested IFs

Why learn it: IFS replaces the nightmare of nested IF(IF(IF(...))) with a clean condition-value pair structure. It's more readable, less error-prone, and directly maps to SQL's CASE WHEN and Python's elif. Bangalore companies love using IFS for tiered commission calculations, customer segmentation, SLA classification, and grading systems. If you're still writing 5-level nested IFs in 2026, you're making your formulas unnecessarily complex.

Example 1: Customer Segment Classification
=IFS( F2>500000, "Platinum", F2>200000, "Gold", F2>50000, "Silver", TRUE, "Bronze" ) /* TRUE at end acts as the "else" — catches everything below Silver threshold */
Example 2: Tiered Commission Calculation
=IFS( F2>1000000, F2*0.08, F2>500000, F2*0.05, F2>100000, F2*0.03, TRUE, F2*0.01 ) /* 8% for >10L, 5% for >5L, 3% for >1L, 1% otherwise */
Example 3: SLA Status Based on Response Time
=IFS( G2<=2, "Met - Excellent", G2<=4, "Met - Acceptable", G2<=8, "At Risk", TRUE, "Breached" ) /* G2 = Response time in hours. Used heavily in IT service desk reporting. */
08

COUNTIFS — Multi-Conditional Counting

Why learn it: COUNTIFS is SUMIFS's sibling for counting instead of summing. It answers questions like "how many orders were placed in Bangalore for Electronics in Q1?" This formula is the backbone of KPI dashboards — counting unique customers, tracking ticket volumes, measuring conversion rates. It maps directly to SQL's COUNT with WHERE and DAX's COUNTROWS with FILTER. Every data analyst in Bangalore uses this daily.

Example 1: Count Orders by Region and Category
=COUNTIFS(B:B, "Bangalore", C:C, "Electronics") /* Count of orders where Region=Bangalore AND Category=Electronics */
Example 2: Count with Date Range Condition
=COUNTIFS(D:D, ">="&DATE(2026,1,1), D:D, "<="&DATE(2026,3,31), E:E, "Closed") /* Count closed tickets in Q1 2026 — common in IT service reporting */
Example 3: Conversion Rate Calculation
=COUNTIFS(H:H,"Converted")/COUNTA(H:H) /* Conversion rate = Converted leads / Total leads. Format as percentage. */
09

UNIQUE + SORT — Extract and Organize Distinct Values

Why learn it: These dynamic array functions (Excel 365) replace the old Remove Duplicates manual process and complex SUMPRODUCT-based distinct counts. UNIQUE extracts distinct values from a range. SORT orders them. Together, they power dynamic dropdown lists, automated data validation, and exploratory data analysis without pivot tables. They map to SQL's SELECT DISTINCT and Python's df.unique().

Example 1: Build Dynamic Dropdown Source List
=SORT(UNIQUE(B2:B500)) /* Returns sorted unique regions. Use this as Data Validation source for dropdowns. */
Example 2: Count of Distinct Values
=ROWS(UNIQUE(A2:A1000)) /* Count distinct customers — equivalent to SQL's COUNT(DISTINCT customer_id) */
Example 3: Unique Combinations (Two Columns)
=UNIQUE(HSTACK(B2:B500, C2:C500)) /* Returns unique Region+Category combinations. HSTACK combines two columns side by side. */

Power Query — The Formula Engine Behind Data Cleaning

Why learn it: Power Query isn't a single formula — it's a complete data transformation language (M) built into Excel and Power BI. We include it as the #10 "formula" because it's the most important data preparation skill you can learn. Power Query handles tasks that would take 100 formulas and 2 hours in 3 clicks and 30 seconds: unpivoting data, merging files, splitting columns, removing duplicates, changing data types, and appending tables. Every data analyst in Bangalore uses Power Query daily — it's the bridge between raw data and analysis.

Example 1: Clean Messy Data with Power Query Steps
// Power Query Applied Steps for cleaning sales data: Source = Excel.CurrentWorkbook(){[Name="SalesData"]}[Content] RemovedBlanks = Table.SelectRows(Source, each [OrderID] <> null) ChangedTypes = Table.TransformColumnTypes(RemovedBlanks,{{"Sales", type number}}) SplitColumn = Table.SplitColumn(ChangedTypes, "CustomerName", Splitter.ByDelimiter(" ")) // These steps are recorded automatically — no coding required for basic cleaning
Example 2: Merge Multiple Excel Files into One Table
// Instead of manually copying 50 files: Source = Folder.Files("C:\Sales\Data\") Filtered = Table.SelectRows(Source, each [Extension] = ".xlsx") Combined = Table.Combine(Filtered[Content]) // One-click to merge ALL files in a folder into a single table. Game changer.

// Convert month columns (Jan, Feb, Mar...) into rows: Unpivoted = Table.UnpivotOtherColumns(Source, {"Product", "Region"}, "Month", "Sales") // Cross-tab format (wide) → Database format (long). Required before loading to Power BI.

Top 10 Power BI DAX Formulas That Get You Hired

Power BI is the most in-demand data tool in Bangalore — 73% of job postings mention it. But the real differentiator in interviews isn't "knowing Power BI" — it's DAX fluency. DAX (Data Analysis Expressions) is Power BI's formula language, and it's deceptively complex. These 10 DAX formulas are selected based on frequency in Bangalore job interviews and real-world usage at companies like Microsoft, Amazon, Dell, and Infosys.

01

CALCULATE — The Most Important DAX Function Period

Why learn it: CALCULATE is used in 90% of all DAX measures. It modifies the filter context of an expression — meaning it can calculate a sum for a specific region while your report is filtered to a different region, or calculate a percentage of total regardless of slicer selections. If you only learn ONE DAX function, make it CALCULATE. It's the equivalent of SQL's WHERE clause, Excel's SUMIFS, and Python's .loc[] — all combined into one function with far more power.

Example 1: Sales for a Specific Region (Override Filter Context)
Bangalore Sales = CALCULATE( [Total Sales], Sales[Region] = "Bangalore" ) /* Even if the user selects "Mumbai" in the slicer, this measure shows Bangalore sales */
Example 2: Percentage of Total Sales
% of Total = DIVIDE( [Total Sales], CALCULATE([Total Sales], ALL(Sales[Region])) ) /* ALL removes region filter → gives grand total → divide current by grand total */
Example 3: Sales in Previous Year (Time Intelligence)
PY Sales = CALCULATE( [Total Sales], SAMEPERIODLASTYEAR(Date[Date]) ) /* Compare current year vs previous year — the foundation of YoY growth calculations */
02

FILTER — Table-Level Conditional Filtering

Why learn it: While CALCULATE with simple conditions handles basic cases, FILTER is needed for complex conditions — comparisons between columns, aggregate conditions (e.g., "regions where average sale > 50000"), and dynamic filters based on measures. FILTER returns a table, not a value, so it's always used inside CALCULATE or other table functions. Understanding FILTER is what separates DAX beginners from intermediates.

Example 1: Sales for High-Value Products Only
High-Value Sales = CALCULATE( [Total Sales], FILTER(Product, Product[Price] > 10000) ) /* Only sum sales where the product price is > 10,000 — can't do this with simple CALCULATE syntax */
Example 2: Top Performing Regions by Sales
Top Regions Sales = CALCULATE( [Total Sales], FILTER( ALL(Sales[Region]), [Total Sales] > 500000 ) ) /* Filter regions where their total sales exceed 5L — uses a measure inside filter condition */
Example 3: Dynamic Date Range Filtering
Custom Range Sales = CALCULATE( [Total Sales], FILTER( ALL(Date[Date]), Date[Date] >= DATE(2026,1,1) && Date[Date] <= DATE(2026,3,31) ) ) /* Calculate sales for any custom date range regardless of time slicer selection */
03

ALL / ALLEXCEPT — Filter Context Removal

Why learn it: ALL removes filters from a table or column. ALLEXCEPT removes filters from all columns EXCEPT the ones you specify. These functions are essential for calculating percentages of total, grand totals in filtered contexts, and benchmark comparisons. Without ALL, your CALCULATE measures can't "see past" the current filter context — you'd be stuck with only context-aware calculations. This is the #2 most asked DAX concept in interviews.

Example 1: Grand Total Regardless of Selections
Grand Total = CALCULATE([Total Sales], ALL(Sales)) /* ALL(Sales) removes ALL filters from the Sales table → always returns grand total */
Example 2: Percentage of Category Within Region
% of Region = DIVIDE( [Total Sales], CALCULATE([Total Sales], ALLEXCEPT(Sales, Sales[Region])) ) /* ALLEXCEPT keeps Region filter, removes all others → gives region total as denominator */
Example 3: Count of All Products (Ignoring Filters)
Total Products = CALCULATE( COUNTROWS(Product), ALL(Product) ) /* Always shows total product count, even when a category slicer is active */
04

SUMX / AVERAGEX — Row-Level Iteration (X Functions)

Why learn it: The "X" functions (SUMX, AVERAGEX, MINX, MAXX, COUNTX) are iterator functions — they go row by row, evaluate an expression, and then aggregate the result. This is fundamentally different from SUM or AVERAGE, which aggregate column values directly. SUMX is needed when your calculation requires row-level logic first — like multiplying quantity × price per row, then summing. This maps to Python's df.apply() and is critical for calculated columns vs measures understanding.

Example 1: Total Revenue (Quantity × Price Per Row)
Total Revenue = SUMX( Sales, Sales[Quantity] * RELATED(Product[UnitPrice]) ) /* For each row: get quantity from Sales, get price from Product table, multiply, then sum all */
Example 2: Average Order Value
Avg Order Value = AVERAGEX( VALUES(Sales[OrderID]), [Total Sales] ) /* VALUES gets unique orders, AVERAGEX calculates total sales per order, then averages them */
Example 3: Weighted Average Margin
Wtd Avg Margin = SUMX( Sales, (Sales[Revenue] - Sales[Cost]) / Sales[Revenue] * Sales[Revenue] ) / [Total Revenue] /* Row-level margin × revenue weight, summed, divided by total revenue = weighted average */
05

RANKX — Ranking Values in DAX

Why learn it: RANKX ranks items within a table based on an expression. It's used for Top N/Bottom N analysis, leaderboard dashboards, performance ranking by region/product/employee, and conditional formatting triggers. Every business dashboard in Bangalore has a "Top 10 Products" or "Region Ranking" visual — RANKX powers those. It maps to SQL's ROW_NUMBER() OVER (ORDER BY...) and Python's df.rank().

Example 1: Rank Products by Total Sales
Product Rank = RANKX( ALL(Product[ProductName]), [Total Sales], , DESC, DENSE ) /* Rank all products by sales descending. DENSE = no gaps in ranking (1,2,2,3 not 1,2,2,4) */
Example 2: Dynamic Top N Filter
Top 5 Flag = IF( RANKX(ALL(Sales[Region]), [Total Sales],, DESC) <= 5, "Top 5", "Others" ) /* Use this in a visual-level filter to show only Top 5 regions or group rest as "Others" */
Example 3: Rank Within Category
Category Rank = RANKX( FILTER(ALL(Product), Product[Category] = SELECTEDVALUE(Product[Category])), [Total Sales],, DESC ) /* Rank products within their own category, not across all categories */
06

RELATED — Cross-Table Data Fetching

Why learn it: RELATED fetches a value from a related table using the active relationship. In a proper star schema (Sales fact → Product dim → Category dim), you often need to pull columns from dimension tables into your fact table calculations. RELATED does this without creating calculated columns that bloat your model. It's the DAX equivalent of SQL's JOIN and Excel's XLOOKUP. Understanding RELATED also teaches you how Power BI's data model relationships actually work.

Example 1: Pull Category Name into Sales Calculation
Category Sales = CALCULATE( [Total Sales], FILTER(Sales, RELATED(Product[Category]) = "Electronics") ) /* RELATED goes from Sales table → Product table to get Category column value */
Example 2: Build a Full Product Description String
Product Desc = RELATED(Product[Name]) & " (" & RELATED(Product[Category]) & " - " & RELATED(Product[SubCategory]) & ")" /* Creates: "MacBook Pro (Electronics - Laptops)" from three different tables */
Example 3: Conditional Logic Based on Related Table
Priority Flag = IF( RELATED(Customer[Tier]) = "Platinum", "High Priority", "Standard" ) /* Use customer tier from Customer table to flag orders in Sales table */
07

DATEADD — Shift Dates by Intervals

Why learn it: DATEADD shifts a date column forward or backward by a specified number of days, months, quarters, or years. It's the foundation of all time-shifted calculations — previous month, next quarter, 30 days ago. Combined with CALCULATE, it enables rolling averages, period comparisons, and trend analysis. This is the most versatile time intelligence function and is used in virtually every business dashboard.

Example 1: Previous Month Sales
PM Sales = CALCULATE( [Total Sales], DATEADD(Date[Date], -1, MONTH) ) /* Shift date back by 1 month → get previous month's sales for comparison */
Example 2: 3-Month Rolling Average
3M Avg = AVERAGEX( DATESINPERIOD(Date[Date], LASTDATE(Date[Date]), -3, MONTH), [Total Sales] ) /* Average of current month + 2 previous months — smooths out volatility */
Example 3: Quarter-over-Quarter Growth
QoQ Growth = DIVIDE( [Total Sales] - CALCULATE([Total Sales], DATEADD(Date[Date], -1, QUARTER)), CALCULATE([Total Sales], DATEADD(Date[Date], -1, QUARTER)) ) /* (Current Q Sales - Previous Q Sales) / Previous Q Sales → QoQ growth % */
08

TOTALYTD / TOTALQTD / TOTALMTD — Period-to-Date Calculations

Why learn it: YTD, QTD, and MTD calculations are the most requested KPIs in every business. TOTALYTD calculates the sum from the start of the year to the current date context. It automatically handles fiscal year boundaries if configured. Every CFO dashboard, sales report, and performance review uses YTD numbers. If you can't write a TOTALYTD measure in your sleep, you're not ready for a data analyst role in Bangalore.

Example 1: Year-to-Date Revenue
YTD Revenue = TOTALYTD([Total Sales], Date[Date]) /* Sums sales from Jan 1 of selected year to the current filter context date */
Example 2: YTD for Fiscal Year (Apr-Mar)
FY YTD = TOTALYTD( [Total Sales], Date[Date], "31-03" /* Fiscal year ends March 31 (Indian fiscal year) */ ) /* Critical for Indian companies that follow Apr-Mar fiscal year */
Example 3: YTD vs Same Period Last Year
YTD vs LY = DIVIDE( [YTD Revenue] - [CALCULATE([YTD Revenue], SAMEPERIODLASTYEAR(Date[Date]))], [CALCULATE([YTD Revenue], SAMEPERIODLASTYEAR(Date[Date]))] ) /* Compare this year's YTD with same period last year — the #1 executive KPI */
09

SWITCH — DAX's Clean Conditional Logic

Why learn it: SWITCH is DAX's version of Excel's IFS or SQL's CASE WHEN. It evaluates an expression against multiple possible results and returns the first match. It's cleaner than nested IFs, faster to write, and easier to maintain. Used heavily for dynamic measure selection (slicer that switches between different calculations), categorization, and mapping codes to labels. Bangalore companies love SWITCH for creating "View by: Revenue / Quantity / Margin" toggle measures.

Example 1: Dynamic Measure Selection via Slicer
Dynamic Measure = SWITCH( SELECTEDVALUE(MeasureTable[MeasureName]), "Revenue", [Total Sales], "Quantity", [Total Quantity], "Profit", [Total Profit], [Total Sales] /* Default if nothing selected */ ) /* One visual, one measure — user switches between Revenue/Quantity/Profit via slicer */
Example 2: Map Status Codes to Labels
Status Label = SWITCH( Orders[StatusCode], "P", "Pending", "S", "Shipped", "D", "Delivered", "C", "Cancelled", "Unknown" ) /* Maps database codes to user-friendly labels — alternative to a mapping table */
Example 3: Bucket Values into Ranges
Sales Bucket = SWITCH( TRUE(), [Total Sales] >= 1000000, "> 10L", [Total Sales] >= 500000, "5L - 10L", [Total Sales] >= 100000, "1L - 5L", "< 1L" ) /* SWITCH(TRUE()) is a powerful pattern for bucketing continuous values */
10

DIVIDE — Safe Division with Error Handling

Why learn it: DIVIDE is Power BI's safe division function — it handles divide-by-zero errors gracefully by returning an alternate result instead of Infinity or NaN. Using regular "/" in DAX is considered bad practice because it produces ugly errors when the denominator is blank or zero. DIVIDE is used in EVERY percentage calculation, ratio, and rate metric. If you're still using "/" in DAX measures, that's an immediate red flag in interviews. Microsoft's own DAX best practices mandate DIVIDE.

Example 1: Safe Percentage Calculation
% of Total = DIVIDE([Total Sales], [Grand Total Sales], 0) /* Returns 0 instead of Infinity if Grand Total is zero. Third parameter is the alternate result. */
Example 2: Conversion Rate
Conversion Rate = DIVIDE( [Converted Leads], [Total Leads], BLANK() ) /* Returns BLANK instead of error if no leads exist. BLANK() is cleaner than 0 for reports. */
Example 3: Margin Percentage with Safety
Margin % = DIVIDE( [Total Revenue] - [Total Cost], [Total Revenue], 0 ) /* (Revenue - Cost) / Revenue. Returns 0 if Revenue is zero, preventing #DIV/0! errors. */

Top 10 SQL Server Formulas for Data Analysts

SQL is the language of data. Every data tool — Power BI, Tableau, Python, Snowflake — ultimately connects to a database, and SQL is how you talk to it. 01

Window Functions: ROW_NUMBER(), RANK(), DENSE_RANK()

Why learn it: Window functions are the #1 differentiator between a junior analyst and a mid-level analyst. They perform calculations across a set of rows related to the current row — without collapsing the result (unlike GROUP BY). ROW_NUMBER is used for pagination, deduplication, and top-N analysis. Every Bangalore interview has at least one window function question.

Example 1: Top 3 Products per Region
SELECT * FROM ( SELECT Region, Product, Sales, ROW_NUMBER() OVER(PARTITION BY Region ORDER BY Sales DESC) AS rn FROM SalesData ) t WHERE rn <= 3;
Example 2: Remove Duplicates (Keep Latest Record)
DELETE FROM ( SELECT *, ROW_NUMBER() OVER( PARTITION BY OrderID ORDER BY ModifiedDate DESC ) AS rn FROM Orders ) t WHERE rn > 1; /* Keeps only the most recent record per OrderID */
Example 3: Running Total per Customer
SELECT CustomerID, OrderDate, Amount, SUM(Amount) OVER( PARTITION BY CustomerID ORDER BY OrderDate ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW ) AS RunningTotal FROM Orders;

CTEs (Common Table Expressions) with WITH Clause

Why learn it: CTEs create temporary named result sets that exist only for the duration of the query. They make complex queries readable, modular, and debuggable. Instead of nesting 5 subqueries, you write 5 CTEs in sequence. In Bangalore interviews, you'll be asked to write queries with 3-4 CTEs chained together. CTEs also enable recursive queries (hierarchies like employee-manager reporting chains).

Example 1: Multi-Step Sales Analysis
WITH MonthlySales AS ( SELECT Region, MONTH(OrderDate) AS Mth, SUM(Amount) AS Sales FROM Orders GROUP BY Region, MONTH(OrderDate) ), RegionTotal AS ( SELECT Region, SUM(Sales) AS Total FROM MonthlySales GROUP BY Region ) SELECT m.Region, m.Mth, m.Sales, r.Total, CAST(m.Sales AS FLOAT)/r.Total AS PctOfRegion FROM MonthlySales m JOIN RegionTotal r ON m.Region = r.Region;
Example 2: Employee-Manager Hierarchy (Recursive CTE)
WITH Hierarchy AS ( SELECT EmpID, Name, ManagerID, 0 AS Level FROM Employees WHERE ManagerID IS NULL UNION ALL SELECT e.EmpID, e.Name, e.ManagerID, h.Level + 1 FROM Employees e JOIN Hierarchy h ON e.ManagerID = h.EmpID ) SELECT * FROM Hierarchy ORDER BY Level, Name;
Example 3: Customer Cohort Analysis
WITH FirstOrder AS ( SELECT CustomerID, MIN(OrderDate) AS FirstDate FROM Orders GROUP BY CustomerID ), Cohort AS ( SELECT DATEFROMPARTS(YEAR(f.FirstDate),MONTH(f.FirstDate),1) AS CohortMonth, COUNT(DISTINCT f.CustomerID) AS Customers FROM FirstOrder f GROUP BY DATEFROMPARTS(YEAR(f.FirstDate),MONTH(f.FirstDate),1) ) SELECT * FROM Cohort ORDER BY CohortMonth;

CASE WHEN — Conditional Logic in SQL

Why learn it: CASE WHEN is SQL's Swiss Army knife for conditional logic. It maps to Excel's IF/IFS, DAX's SWITCH, and Python's if/elif. You'll use it for bucketing values, creating KPI flags, pivoting data without PIVOT, handling NULL replacements, and creating dynamic labels. Every SQL query of moderate complexity uses CASE WHEN. It appears in 100% of Bangalore SQL interview rounds.

Example 1: Customer Segmentation
SELECT CustomerID, TotalPurchase, CASE WHEN TotalPurchase >= 500000 THEN 'Platinum' WHEN TotalPurchase >= 200000 THEN 'Gold' WHEN TotalPurchase >= 50000 THEN 'Silver' ELSE 'Bronze' END AS Segment FROM Customers;
Example 2: Pivot Data Using CASE WHEN
SELECT Region, SUM(CASE WHEN Category='Electronics' THEN Sales ELSE 0 END) AS Electronics, SUM(CASE WHEN Category='Clothing' THEN Sales ELSE 0 END) AS Clothing, SUM(CASE WHEN Category='Food' THEN Sales ELSE 0 END) AS Food FROM SalesData GROUP BY Region; /* Converts rows to columns without using PIVOT — works in all SQL dialects */
Example 3: Conditional Aggregation for KPIs
SELECT COUNT(*) AS TotalOrders, SUM(CASE WHEN Status='Delivered' THEN 1 ELSE 0 END) AS Delivered, SUM(CASE WHEN Status='Cancelled' THEN 1 ELSE 0 END) AS Cancelled, CAST(SUM(CASE WHEN Status='Delivered' THEN 1 ELSE 0 END) AS FLOAT)/COUNT(*) AS DeliveryRate FROM Orders;

Multiple JOINs (INNER, LEFT, RIGHT, FULL)

Why learn it: JOINs are fundamental to SQL, but real-world queries require 4-5 table joins with different types. LEFT JOIN to get all customers even without orders. Example 1: Customer-Order-Product Triple Join
SELECT c.Name, o.OrderDate, p.ProductName, o.Quantity, o.Amount FROM Customers c LEFT JOIN Orders o ON c.CustomerID = o.CustomerID LEFT JOIN Products p ON o.ProductID = p.ProductID WHERE c.Region = 'Bangalore'; /* LEFT JOIN ensures customers with zero orders still appear */

SELECT o.OrderID, o.CustomerID FROM Orders o LEFT JOIN Customers c ON o.CustomerID = c.CustomerID WHERE c.CustomerID IS NULL; /* Orders with invalid CustomerID — orphan records. Critical data quality check. */

SELECT e.Name AS Employee, m.Name AS Manager, e.Salary FROM Employees e INNER JOIN Employees m ON e.ManagerID = m.EmpID WHERE e.Salary > m.Salary; /* Find employees who earn more than their manager — classic interview question */

GROUP BY with HAVING and Aggregate Functions

Why learn it: GROUP BY with aggregates (SUM, COUNT, AVG, MIN, MAX) is SQL's core analytical capability. HAVING filters groups after aggregation (WHERE filters before). Example 1: Top Regions by Average Order Value
SELECT Region, COUNT(*) AS Orders, AVG(Amount) AS AvgOrder FROM Orders GROUP BY Region HAVING AVG(Amount) > 5000 ORDER BY AvgOrder DESC;
Example 2: Multi-Level Subtotals with GROUPING SETS
SELECT Region, Category, SUM(Sales) AS TotalSales FROM SalesData GROUP BY GROUPING SETS( (Region, Category), (Region), () ); /* Returns: Region+Category subtotals, Region subtotals, and Grand Total — all in one query */

SELECT Email, COUNT(*) AS DupCount FROM Customers GROUP BY Email HAVING COUNT(*) > 1; /* Find all duplicate email addresses — common data cleaning task */

Correlated Subqueries

Why learn it: A correlated subquery references the outer query for each row — it runs once per row instead of once for the entire query. This enables comparisons like "find customers whose order amount is above their region's average." While often replaceable by window functions, correlated subqueries still appear in interviews and legacy codebases. Understanding them also deepens your grasp of SQL execution flow.

Example 1: Customers Above Their Region Average
SELECT Name, Region, TotalPurchase FROM Customers c WHERE TotalPurchase > ( SELECT AVG(TotalPurchase) FROM Customers WHERE Region = c.Region );
Example 2: Orders Larger Than Customer's Average
SELECT o.OrderID, o.CustomerID, o.Amount FROM Orders o WHERE o.Amount > ( SELECT AVG(Amount) FROM Orders WHERE CustomerID = o.CustomerID );
Example 3: EXISTS for Matching Records
SELECT c.Name, c.Email FROM Customers c WHERE EXISTS ( SELECT 1 FROM Orders o WHERE o.CustomerID = c.CustomerID AND o.Amount > 100000 ); /* Find customers who have at least one order above 1L — EXISTS is faster than JOIN for this */

COALESCE and ISNULL — NULL Handling

Why learn it: NULL is SQL's most misunderstood concept. NULL != 0, NULL != empty string, NULL != NULL. COALESCE returns the first non-NULL value from a list. ISNULL (SQL Server specific) replaces NULL with a specified value. These functions are essential for cleaning data, providing default values, and preventing NULL propagation in calculations. Every real-world dataset has NULLs — knowing how to handle them is non-negotiable.

Example 1: Replace NULL with Default
SELECT Name, COALESCE(Phone, 'N/A') AS Phone, COALESCE(Email, Phone, 'No Contact') AS PrimaryContact FROM Customers; /* Try Email first, if NULL try Phone, if both NULL show 'No Contact' */
Example 2: NULL-Safe Aggregation
SELECT Region, SUM(COALESCE(Discount, 0)) AS TotalDiscount, AVG(COALESCE(Rating, 0)) AS AvgRating FROM SalesData GROUP BY Region; /* Without COALESCE, SUM ignores NULLs (OK) but AVG excludes them (may be misleading) */
Example 3: Priority Column Selection
SELECT OrderID, COALESCE(DeliveryAddress, BillingAddress, OfficeAddress) AS ShipTo FROM Orders; /* Use delivery address if available, else billing, else office — cascading fallback */

PIVOT and UNPIVOT

Why learn it: PIVOT converts rows to columns (cross-tab format). UNPIVOT converts columns to rows (normalized format). Business users love cross-tabs (months as columns, categories as columns). Databases store data normalized (one value per row). PIVOT/UNPIVOT bridge this gap. While CASE WHEN can do simple pivoting, PIVOT handles dynamic scenarios more elegantly. This is especially important when preparing data for Power BI — sometimes you need to pivot before loading.

Example 1: Pivot Monthly Sales by Region
SELECT Region, [Jan], [Feb], [Mar], [Apr], [May], [Jun] FROM ( SELECT Region, DATENAME(MONTH, OrderDate) AS Mth, Sales FROM Orders ) s PIVOT (SUM(Sales) FOR Mth IN ([Jan],[Feb],[Mar],[Apr],[May],[Jun])) AS p;
Example 2: UNPIVOT for Normalization
SELECT Region, Metric, Value FROM RegionSummary UNPIVOT (Value FOR Metric IN ([Revenue], [Profit], [Customers])) AS u; /* Converts columns Revenue/Profit/Customers into rows with Metric/Value pairs */
Example 3: Dynamic PIVOT with Stored Procedure
DECLARE @cols NVARCHAR(MAX), @sql NVARCHAR(MAX); SELECT @cols = STRING_AGG(QUOTENAME(Category), ',') FROM (SELECT DISTINCT Category FROM SalesData) t; SET @sql = 'SELECT Region, ' + @cols + ' FROM SalesData PIVOT (SUM(Sales) FOR Category IN (' + @cols + ')) p'; EXEC sp_executesql @sql; /* Dynamic PIVOT — automatically discovers categories and pivots them */

Date Functions: DATEDIFF, DATEADD, EOMONTH

Why learn it: Every business question involves time: "How long since the last order?" "What's the average delivery time?" "Show me month-end balances." SQL Server's date functions handle these calculations. DATEDIFF calculates the difference between dates. DATEADD shifts dates. EOMONTH returns the last day of the month. These are essential for churn analysis, SLA tracking, and time-based filtering.

Example 1: Days Between Order and Delivery
SELECT OrderID, DATEDIFF(DAY, OrderDate, DeliveryDate) AS DeliveryDays, CASE WHEN DATEDIFF(DAY, OrderDate, DeliveryDate) <= 3 THEN 'On Time' ELSE 'Late' END AS SLAStatus FROM Orders;
Example 2: Customer Churn Detection
SELECT c.CustomerID, c.Name, DATEDIFF(DAY, MAX(o.OrderDate), GETDATE()) AS DaysSinceLastOrder FROM Customers c LEFT JOIN Orders o ON c.CustomerID = o.CustomerID GROUP BY c.CustomerID, c.Name HAVING DATEDIFF(DAY, MAX(o.OrderDate), GETDATE()) > 90; /* Customers who haven't ordered in 90+ days — likely churned */

WITH Monthly AS ( SELECT EOMONTH(OrderDate) AS MonthEnd, SUM(Amount) AS Sales FROM Orders GROUP BY EOMONTH(OrderDate) ) SELECT m.MonthEnd, m.Sales, p.Sales AS PrevMonthSales, (m.Sales - p.Sales) / NULLIF(p.Sales, 0) * 100 AS GrowthPct FROM Monthly m LEFT JOIN Monthly p ON DATEADD(MONTH, 1, p.MonthEnd) = m.MonthEnd;

Why Power BI Wins in Bangalore — The Detailed Case

1. Job Market Dominance is Overwhelming

73% of data analytics job postings in Bangalore mention Power BI. 28% mention Tableau (most of these also mention Power BI). Only 15% mention Looker Studio, 12% QuickSight. The gap between Power BI and every other tool isn't narrowing — it's widening. Why? Because Microsoft 365 is universal in corporate India. Every company already has Microsoft licenses. Power BI Pro ($10/user/month) is a checkbox add-on. Tableau ($70-$150/user/month) requires a separate budget approval. In cost-conscious Indian companies, this alone decides the winner.

2. DAX is More Valuable Than Tableau's LOD

DAX is harder to learn than Tableau's calculated fields — but that's actually an advantage. When DAX clicks for you, you've developed a deep understanding of filter context, evaluation context, and data modeling that transfers to every other tool. Tableau's LOD expressions are powerful but simpler to grasp, which means less interview differentiation. In Bangalore interviews, demonstrating DAX expertise signals deeper analytical thinking.

3. Microsoft Fabric Changes Everything in 2026

Microsoft Fabric — launched in 2023, mature in 2026 — integrates Power BI with data engineering (Data Factory), data science (ML experiments), real-time analytics (Eventstreams), and data warehousing (Lakehouse) in one platform. Power BI isn't just a visualization tool anymore — it's the frontend for the entire Microsoft data platform. Tableau has no equivalent to this depth of integration. When a company adopts Fabric, Power BI becomes the default — and Fabric adoption in Bangalore is accelerating because it replaces 5-6 separate tools (Snowflake + dbt + Fivetran + Tableau + Jupyter) with one Microsoft subscription.

4. Copilot AI Integration

Power BI's Copilot (powered by GPT-4) can generate DAX measures from natural language, create report layouts, write M query transformations, and explain insights in plain English. In 2026, Copilot has matured from a gimmick to a genuine productivity multiplier. Tableau's "Ask Data" is less capable. QuickSight's Q is good but limited to AWS context. Power BI's Copilot is the most widely usable AI assistant in BI.

5. Certification Path is Clearer

Microsoft's certification path — PL-300 (Power BI Data Analyst Associate) → PL-400 (Power BI Developer) → Expert-level — is well-recognized in Bangalore. Having PL-300 on your resume gets you past initial resume screening filters at most companies. Tableau's certification is respected but less frequently listed as a requirement. QuickSight and Looker Studio have no widely recognized certification paths. For a fresher or career-switcher in Bangalore, PL-300 is the highest-ROI certification investment.

6. Community and Learning Resources Are Unmatched

Power BI has the largest BI community in the world. YouTube tutorials (SQLBI, Curbal, Enterprise DNA), forums (Microsoft Q&A, Reddit r/PowerBI), free datasets (Microsoft GitHub sample models), and blogs outnumber Tableau resources 3:1. In Bangalore specifically, the Power BI user group meets monthly, and there are more local Power BI trainers than Tableau trainers. More resources = faster learning = faster job readiness.

7. When Tableau Still Makes Sense

We're not saying Tableau is bad. It's excellent — and in specific scenarios, it's better than Power BI:

  • Consulting firms (McKinsey, BCG, Deloitte) standardized on Tableau pre-acquisition and haven't fully migrated.
  • Visual analytics depth — Tableau's drag-and-drop visual exploration is still more intuitive than Power BI for ad-hoc analysis.
  • Large datasets — Tableau's Hyper engine handles 10B+ row datasets slightly better than Power BI's Import mode (though Power BI's DirectQuery to Fabric/Snowflake mitigates this).
  • Specific target companies — if your dream company uses Tableau, learn Tableau. Tool fluency matters more than market share for your specific job.
