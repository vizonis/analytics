Chapter 01

TEXT FUNCTIONS

Search, extract, and manipulate text in DAX columns

Text

CONTAINSSTRING

// Check if Job Title contains "Manager" Is Manager = CONTAINSSTRING( HR[Job Title], "Manager" )
How it works

Scans each Job Title for the substring "Manager":
"Sr. Manager" → TRUE
"Computer Systems Manager" → TRUE
"Technical Architect" → FALSE
"Director" → FALSE

Returns TRUE/FALSE. Case-insensitive. Use inside FILTER to find matching rows.

Text

CONTAINSSTRING — Practical

// Count all Manager-level employees Manager Count = CALCULATE( COUNTROWS( HR ), FILTER( HR, CONTAINSSTRING( HR[Job Title], "Manager" ) ) )
Result

Matches: "Sr. Manger" (note typo in data), "Computer Systems Manager", "Engineering Manager", "IT Coordinator" — no. Only rows where "Manager" appears as substring. From 315 rows, approximately 40-50 rows match.

Text

LEFT / STARTSWITH

// Extract first 2 characters of EEID EEID Prefix = LEFT( HR[EEID], 2 ) // Result: "E0" for all rows // Check if EEID starts with "E02" Starts E02 = STARTSWITH( HR[EEID], "E02" )
How it works

LEFT(text, num_chars) — Extracts characters from the left.
E02387 → LEFT(..., 2) → "E0"
E04105 → LEFT(..., 2) → "E0"

STARTSWITH(text, prefix) — Returns TRUE/FALSE.
E02572 starts with "E02"? → TRUE
E04105 starts with "E02"? → FALSE

Text

RIGHT / ENDSWITH

// Extract last 4 characters of EEID EEID Suffix = RIGHT( HR[EEID], 4 ) // Result: "2387" for E02387 // Check if EEID ends with "05" Ends 05 = ENDSWITH( HR[EEID], "05" )
How it works

RIGHT(text, num_chars) — Extracts from the right.
E02387 → RIGHT(..., 4) → "2387"
E04105 → RIGHT(..., 4) → "4105"

ENDSWITH — Returns TRUE/FALSE.
E04105 ends with "05"? → TRUE
E02387 ends with "05"? → FALSE

Chapter 02

TIME INTELLIGENCE FUNCTIONS

Calculate MTD, QTD, YTD and navigate time periods — the most requested DAX skill in job interviews

Prerequisite: You Need a Date Table

ALL time intelligence functions require a separate Date table marked as "Date table" in Power BI. If you don't have one, create it:

DateTable = CALENDARAUTO() // Then: Table Tools → Mark as Date Table → Select the Date column

The Date table must have a continuous range of dates and a relationship to your HR table's Hire Date column.

Time Intel

TOTALMTD

// Total hires from start of month to current date Hires MTD = CALCULATE( COUNTROWS( HR ), TOTALMTD( DateTable[Date], LASTDATE( DateTable[Date] ) ) )
Example

If your visual is filtered to March 2021:
MTD = hires from March 1 to March 31 = John Chow (Mar 11) + Lillian Park (Feb 24 — no, not in March) = depends on date range.

TOTALMTD automatically calculates from the 1st of the current month.

Time Intel

TOTALQTD

// Total hires from start of quarter to current date Hires QTD = CALCULATE( COUNTROWS( HR ), TOTALQTD( DateTable[Date], LASTDATE( DateTable[Date] ) ) )
Example

If filtered to Q1 2021 (Jan-Mar):
QTD = hires from Jan 1 to Mar 31 = all hires in Jan + Feb + Mar 2021.

Quarter boundaries: Q1=Jan-Mar, Q2=Apr-Jun, Q3=Jul-Sep, Q4=Oct-Dec.

Time Intel

TOTALYTD

// Total hires from Jan 1 to current date in the year Hires YTD = CALCULATE( COUNTROWS( HR ), TOTALYTD( DateTable[Date], LASTDATE( DateTable[Date] ) ) )
Example

If filtered to Aug 2021:
YTD = hires from Jan 1, 2021 to Aug 31, 2021.
Includes: John Chow (Mar 11), Lillian Park (Feb 24), etc.

Most commonly used time intelligence function in HR dashboards.

Time Intel

TOTALYTD — Custom Fiscal Year

// YTD starting from April 1 (Indian FY) Hires YTD Fiscal = CALCULATE( COUNTROWS( HR ), TOTALYTD( DateTable[Date], LASTDATE( DateTable[Date] ), 3, 31 ) )
How it works

The 4th and 5th parameters set month end number (3 = March) and day (31). So fiscal year starts April 1.

If current date is June 2021, YTD Fiscal = April 1 to June 30, 2021.

PREVIOUSMONTH shifts to March 2021.
Returns count of hires in March 2021.

PREVIOUSQUARTER = Q1 2021 (Jan-Mar).
Returns count of hires in Jan-Mar 2021.

PREVIOUSYEAR = entire year 2020.
Returns count of all hires in 2020.

PREVIOUSDAY

Example

If current is March 12, 2021:
PREVIOUSDAY = March 11, 2021.
Returns: 1 (John Chow hired on Mar 11).

Chapter 03

DATEDIFF

Calculate the difference between two dates in any unit — the foundation of tenure calculations

DATEDIFF Syntax

DATEDIFF( StartDate, EndDate, "UNIT" )

Units: YEAR, QUARTER, MONTH, DAY, HOUR, MINUTE, SECOND

Note: In DAX, the order is StartDate, EndDate, Unit. In Power Query it's reversed. Don't mix them up!

DATEDIFF

YEAR

// Tenure in complete years Tenure Years = DATEDIFF( HR[Hire Date], IF( ISBLANK( HR[Exit Date] ), TODAY(), HR[Exit Date] ), "YEAR" )
Results

Emily Davis: 2016/4/8 to 2021/10/16 = 5 years
Theodore Dinh: 1997/11/29 to Today = 27 years
Owen Lam: 2017/5/29 to 2017/7/16 = 0 years (only 1.5 months)

YEAR counts complete years only (truncates, doesn't round).

DATEDIFF

MONTH

// Tenure in complete months Tenure Months = DATEDIFF( HR[Hire Date], IF( ISBLANK( HR[Exit Date] ), TODAY(), HR[Exit Date] ), "MONTH" )
Results

Emily Davis: 2016/4/8 to 2021/10/16 = 66 months
Owen Lam: 2017/5/29 to 2017/7/16 = 1 month
Lillian Park: 2021/2/24 to 2021/11/10 = 8 months

More precise than YEAR for short-tenured employees.

DATEDIFF

DAY

// Tenure in exact days Tenure Days = DATEDIFF( HR[Hire Date], IF( ISBLANK( HR[Exit Date] ), TODAY(), HR[Exit Date] ), "DAY" )
Results

Emily Davis: = 2018 days
Owen Lam: 2017/5/29 to 2017/7/16 = 48 days

Most granular. Use for precise tenure or for converting to decimal years (days/365.25).

DATEDIFF

HOUR / MINUTE

// If you have datetime columns (time of exit etc.) Hours Worked = DATEDIFF( HR[Shift Start], HR[Shift End], "HOUR" ) Minutes Diff = DATEDIFF( HR[Shift Start], HR[Shift End], "MINUTE" )
Use Case

HOUR/MINUTE are used for attendance tracking, shift calculations, SLA compliance. Our HR data only has dates (no times), so these would apply if you had datetime columns.

HR DAX ASSIGNMENT

4 real-world calculations using the attached HR data

Q1: Average Tenure Using Hire Date and Exit Date

// Step 1: Calculated Column — Tenure in Days Tenure Days = DATEDIFF( HR[Hire Date], IF( ISBLANK( HR[Exit Date] ), TODAY(), HR[Exit Date] ), "DAY" ) // Step 2: Measure — Average Tenure in Years Avg Tenure (Years) = AVERAGE( HR[Tenure Days] ) / 365.25
How it works

Step 1 creates a calculated column that computes tenure for each row. Active employees use TODAY() as end date. InActive employees use their Exit Date.

Step 2 averages all tenure days and divides by 365.25 to convert to years.

Emily Davis: 2018 days / 365.25 = 5.52 years
Theodore Dinh: ~9930 days / 365.25 = 27.18 years
Owen Lam: 48 days / 365.25 = 0.13 years

With 315 employees spanning 1992-2021, average would be approximately 9-11 years.

Q2: Total Employees Onboarded by Each Month (MTD)

// Assumes DateTable is linked to HR[Hire Date] Hires MTD = CALCULATE( COUNTROWS( HR ), TOTALMTD( DateTable[Date] ) )
How it works

TOTALMTD returns all dates from the 1st of the current month to the current date context.

Put this in a matrix visual with months on rows:
Jan 2021 → hires from Jan 1-31, 2021
Feb 2021 → hires from Feb 1-28, 2021 (includes Lillian Park: Feb 24)
Mar 2021 → hires from Mar 1-31, 2021 (includes John Chow: Mar 11)

Each cell automatically calculates MTD based on its row context.

Q3: Total Employees Onboarded YTD

Hires YTD = CALCULATE( COUNTROWS( HR ), TOTALYTD( DateTable[Date] ) )
How it works

TOTALYTD returns all dates from Jan 1 of the selected year to the current date context.

If your visual shows 2021:
YTD = all hires from Jan 1, 2021 to Dec 31, 2021
= Lillian Park (Feb 24) + John Chow (Mar 11) + others hired in 2021

If filtered to March 2021 specifically:
YTD = Jan 1 to Mar 31, 2021

Q4: % Difference from Previous Month

// Step 1: Current month hires Hires Current Month = COUNTROWS( HR ) // Step 2: Previous month hires Hires Prev Month = CALCULATE( COUNTROWS( HR ), PREVIOUSMONTH( DateTable[Date] ) ) // Step 3: % difference % Change vs Prev Month = DIVIDE( [Hires Current Month] - [Hires Prev Month], [Hires Prev Month], 0 )
How it works

DIVIDE safely divides (avoids divide-by-zero errors). Third parameter is the alternate result if division fails.

Example with HR data:
If March 2021 = 3 hires, February 2021 = 1 hire:
% Change = (3 - 1) / 1 = 200%

If February = 0 hires (no data):
DIVIDE returns 0 (the alternate result), not an error.

Format this measure as % in Power BI. Put it in a line chart with months on X-axis to see month-over-month hiring trends.

Chapter 05

ADVANCED TIME INTELLIGENCE

SAMEPERIODLASTYEAR, DATESBETWEEN, DATESINPERIOD

Time Intel

SAMEPERIODLASTYEAR

// Compare this year's hires to last year Hires Last Year = CALCULATE( COUNTROWS( HR ), SAMEPERIODLASTYEAR( DateTable[Date] ) ) // YoY Growth % YoY Growth % = DIVIDE( [Hires YTD] - [Hires Last Year], [Hires Last Year], 0 )
How it works

SAMEPERIODLASTYEAR shifts the entire date context back by one year. If your visual shows Q1 2021, it automatically returns Q1 2020 dates.

Works with any granularity: day, month, quarter, year. The function figures out the right shift automatically.

Time Intel

DATESBETWEEN

// Hires between two specific dates Hires 2019 to 2020 = CALCULATE( COUNTROWS( HR ), DATESBETWEEN( DateTable[Date], DATE( 2019, 1, 1 ), DATE( 2020, 12, 31 ) ) )
How it works

DATESBETWEEN returns a table of dates from Jan 1, 2019 to Dec 31, 2020. CALCULATE then uses this to filter the HR table.

Unlike TOTALYTD which auto-detects the period, DATESBETWEEN lets you specify exact start and end dates.

Time Intel

DATESINPERIOD

// Rolling 3-month hires Rolling 3M Hires = CALCULATE( COUNTROWS( HR ), DATESINPERIOD( DateTable[Date], LASTDATE( DateTable[Date] ), -3, "MONTH" ) )
How it works

DATESINPERIOD(Table, AnchorDate, Offset, Unit) — starts from the anchor date and goes back/forward by the offset.

Parameters:
AnchorDate: LASTDATE(DateTable[Date]) = last date in current filter
Offset: -3 means go back 3 months
Unit: MONTH (also accepts DAY, QUARTER, YEAR)

If current month is March 2021: returns Jan 1 to Mar 31, 2021. If February 2021: returns Dec 2020 to Feb 2021. Perfect for rolling average and moving total charts.

Chapter 06

DAX LOGICAL FUNCTIONS

IF ELSE, Nested IF, and SWITCH — the decision-making engine of DAX

Logical

IF ELSE

// Salary Band — Calculated Column Salary Band = IF( HR[Salary] > 200000, "Executive", "Standard" )
Results

Emily Davis ($141,604) → "Standard"
Robert Yang ($256,420) → "Executive"
Joseph Martin ($247,022) → "Executive"
Penelope Jordan ($84,913) → "Standard"

Logical

Nested IF ELSE

// Multi-level Salary Band Salary Tier = IF( HR[Salary] > 200000, "Tier 1", IF( HR[Salary] > 150000, "Tier 2", IF( HR[Salary] > 100000, "Tier 3", "Tier 4" ) ) )
Results

Robert Yang ($256,420) → "Tier 1"
Luna Sanders ($163,099) → "Tier 2"
Emily Davis ($141,604) → "Tier 3"
Penelope Jordan ($84,913) → "Tier 4"

Works, but gets messy with 4+ levels. Use SWITCH instead.

Logical

SWITCH — The Cleaner Alternative

// Employee Group classification (cleaner than nested IF) Emp Group Label = SWITCH( TRUE(), HR[Salary] > 200000, "Executive Level", HR[Salary] > 150000, "Senior Leadership", HR[Salary] > 100000, "Senior Professional", HR[Salary] > 75000, "Mid Level", "Entry Level" ) // SWITCH on exact match (Employee Status) Status Label = SWITCH( HR[Employee Status], "Active", "Currently Employed", "InActive", "Separated", "Unknown Status" )
Why SWITCH is better

SWITCH(TRUE(), ...) evaluates conditions top-to-bottom and returns the FIRST match. Like a series of IF-ELSE but much more readable.

SWITCH(column, match1, result1, match2, result2, ...) does exact matching. Perfect for mapping codes to labels.

Robert Yang ($256K) → "Executive Level"
Emily Davis ($141K) → "Senior Professional"
Elena Vang ($95K) → "Mid Level"
Joshua Gupta ($50K) → "Entry Level"

Chapter 07

ALL / ALLSELECTED / ALLEXCEPT

The filter-removal functions — critical for percentages, ratios, and comparisons

Why Do We Need These?

Problem: When you put a measure in a visual, it automatically gets filtered by that visual. If you show salary by City, each city bar only shows that city's total. But what if you want to show "what % is this city of the total?" You need to remove the city filter for the denominator.

That's what ALL does — it removes filters so you can calculate the "big picture" number.

Filter Removal

ALL

// Remove ALL filters from a table Total Salary All = CALCULATE( SUM( HR[Salary] ), ALL( HR ) ) // % of Total Salary by City % of Total Salary = DIVIDE( SUM( HR[Salary] ), CALCULATE( SUM( HR[Salary] ), ALL( HR ) ), 0 )
Example

In a bar chart by City:
Seattle bar: $141,604 / ALL total → ~1.3% (just Emily)
Chicago bar: $332,915 / ALL total → ~2.9% (Luna + Penelope + others)

ALL(HR) removes EVERY filter from the HR table — city, department, status, everything. The denominator becomes the grand total.

Filter Removal

ALLSELECTED

// Remove filters EXCEPT external slicer selections % of Selected Total = DIVIDE( SUM( HR[Salary] ), CALCULATE( SUM( HR[Salary] ), ALLSELECTED( HR ) ), 0 )
ALL vs ALLSELECTED

If user selects "United States" in a Country slicer:
ALL: denominator = entire world total (ignores slicer)
ALLSELECTED: denominator = US total only (respects slicer)

Use ALLSELECTED when you want "% of what the user selected" not "% of everything."

Filter Removal

ALLEXCEPT

// Remove all filters EXCEPT City — keep City, remove everything else % of City Total = DIVIDE( SUM( HR[Salary] ), CALCULATE( SUM( HR[Salary] ), ALLEXCEPT( HR, HR[City] ) ), 0 )
How ALLEXCEPT works

ALLEXCEPT(Table, ColumnToKeep) — removes ALL filters from the table EXCEPT the specified column.

In a matrix with City on rows and Status on columns:
ALL: denominator = grand total (ignores both City and Status)
ALLSELECTED: denominator = respects all slicers but removes visual filters
ALLEXCEPT(HR, HR[City]): denominator = city total (ignores Status column but keeps City). So "Seattle Active" / "Seattle Total" = true % within Seattle.

Rule of thumb: ALL = ignore everything. ALLSELECTED = respect slicers. ALLEXCEPT = keep specific column(s).

Chapter 08

USERELATIONSHIP & TREATAS

Advanced relationship manipulation — used in inactive relationships and role-playing dimensions

Relationship

USERELATIONSHIP

// Scenario: Inactive relationship between DateTable // and HR[Exit Date]. Activate it for this measure only. Exits by Month = CALCULATE( COUNTROWS( HR ), USERELATIONSHIP( DateTable[Date], HR[Exit Date] ) )
Why this matters

In HR data, you often need two date relationships: one for Hire Date (active) and one for Exit Date (inactive). Power BI only allows one active relationship between two tables.

USERELATIONSHIP temporarily activates the inactive relationship only for that specific measure. Other measures still use the active Hire Date relationship.

Relationship

TREATAS

// Apply filters from one table to another // even when there's NO relationship between them Salary by Selected Cities = CALCULATE( SUM( HR[Salary] ), TREATAS( VALUES( CitySlicer[City] ), HR[City] ) )
Why this matters

TREATAS moves filters across unrelated tables. If you have a disconnected City slicer table, TREATAS applies its selections to the HR table's City column — without needing a model relationship.

Use cases: dynamic dimension swapping, what-if parameters, disconnected slicer tables.

Chapter 09

DAX RLS FUNCTIONS

Row-Level Security — show different data to different users based on who logged in

What is RLS?

RLS (Row-Level Security) uses DAX to filter data per user. When an HR manager logs in, they see only their department. When the CEO logs in, they see everything. The report URL is the same — DAX decides what each user sees.

Set in: Modeling tab → Manage Roles → Create Role → Paste DAX

RLS

USERNAME()

// Role: City Manager // Shows only rows where user's city matches HR city // Assume USERPRINCIPALNAME() returns // "john@company.com" City Manager Role = HR[City] = LOOKUPVALUE( UserTable[City], UserTable[Email], USERPRINCIPALNAME() )
How it works

USERPRINCIPALNAME() returns the email of the logged-in user.
LOOKUPVALUE finds that user's assigned city in a UserTable.
RLS then filters HR to only show that city's rows.

If john@company.com is mapped to Seattle → sees only Seattle employees (Emily Davis).

RLS

Country-Level RLS

// Role: Country Filter Country Role = HR[Country] IN VALUES( UserTable[Country] ) // Where UserTable is filtered by: // UserTable[Email] = USERPRINCIPALNAME()
How it works

The UserTable has an RLS filter on Email = current user. So VALUES(UserTable[Country]) returns only that user's country. HR is then filtered to that country.

US user → sees only United States rows. China user → sees only China rows.

RLS Gotchas

1

Test in Power BI Desktop — use "View as Roles" to verify before publishing. RLS errors are silent in production.

2

USERPRINCIPALNAME() returns UPN (email), not display name. Match against email in your mapping table.

3

RLS filters are applied BEFORE measures calculate — you don't need CALCULATE inside RLS. The filter is implicit.

4

Dynamic RLS = uses USERPRINCIPALNAME (changes per user). Static RLS = fixed filter, same for all users in that role.

Chapter 10

CRITICAL FUNCTIONS YOU MUST KNOW

These didn't fit the earlier categories but are absolutely essential for production dashboards

Critical

DIVIDE

// Safe division — no divide-by-zero errors Bonus Amount = DIVIDE( HR[Salary], 100, 0 ) // DIVIDE(numerator, denominator, alternate_result)

Always use DIVIDE instead of /. If denominator is 0 or BLANK, DIVIDE returns the alternate result (0) instead of an Infinity error that breaks your visual.

Critical

RELATED

// Fetch Department Name from Dept table // using Dept_ID relationship Dept Name = RELATED( Department[Dept Name] ) // Fetch Business Unit from BU table BU Name = RELATED( BusinessUnit[BU Name] )

RELATED follows relationships to pull columns from related tables. Use in calculated columns when your fact table only has IDs but you need names.

Critical

ISBLANK / COALESCE

// Check if Exit Date is blank (still Active) Is Still Active = ISBLANK( HR[Exit Date] ) // COALESCE — return first non-blank value Display Name = COALESCE( HR[Preferred Name], HR[Full Name], "Unknown" )

ISBLANK is essential for handling missing Exit Dates. COALESCE is like Excel's IFERROR — tries multiple values and returns the first one that isn't blank.

Critical

VALUES / HASONEVALUE

// VALUES — returns unique values in current filter context Selected Cities = VALUES( HR[City] ) // HASONEVALUE — check if exactly one value is selected City Label = IF( HASONEVALUE( HR[City] ), "Showing: " & SELECTEDVALUE( HR[City] ), "Multiple cities selected" )

VALUES returns a table of unique values in the current filter. HASONEVALUE + SELECTEDVALUE are essential for dynamic card titles.

Critical

FORMAT

// Format numbers as currency Salary Text = FORMAT( HR[Salary], "$#,##0" ) // Result: "$256,420" // Format dates Hire Date Text = FORMAT( HR[Hire Date], "MMM YYYY" ) // Result: "Apr 2016"

Use when you need text output from numbers/dates. Don't use FORMAT in measures that need to stay numeric (it converts to text, breaking SUM/CALCULATE).

Critical

RANKX

// Rank employees by salary within each city Salary Rank = RANKX( ALL( HR ), SUM( HR[Salary] ), DESC, SKIP )

RANKX is an iterator that ranks values. DESC = highest first. Put it in a table visual with City to see "Top earner in each city." Essential for HR leaderboards.
